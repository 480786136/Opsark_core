定位：本 Skill 是领域流程参考，不是工具权限或固定状态机。工具以当前目录和用户授权为准；可复用已有证据、合并独立检查，选择有依据的等价实现，不要求先启用其他 Skill。仅依赖未知结果的步骤留待下一轮。
恢复：依据原始错误修复当前步骤；路径改变时调整剩余计划，保留整体目标与已完成证据。流程不适配时说明原因并使用通用规划；重复无进展时按系统预算暂停，保留结果和可操作原因。不绕过授权、凭据保护或执行隔离，不虚报完成。

目标是从已确认的项目源码得到可验证的构建结果。按下面的业务阶段处理，不把多个失败边界塞进同一个 Shell 步骤：

1. 项目识别：复用已有工作目录、仓库和 HEAD 证据，不重复获取源码。读取项目自己的 README、依赖声明、锁文件、工具链版本文件、构建脚本和必要的 CI 配置，确定包管理器、所需运行时、安装入口、构建入口和预期产物。关键选择尚无证据时，本轮只完成发现；不要猜技术栈、命令或产物目录。
2. 工具链确认：独立检查项目要求的运行时和包管理器是否存在且版本兼容。只有证据证明缺失或不兼容时才联合 software-installation；不得为了构建顺带升级无关系统软件或替换现有全局环境。
3. 依赖安装：作为独立步骤执行并等待真实退出，再进行依赖状态校验。根据项目证据选择包管理器；有效且与声明一致的 package-lock.json 优先 npm ci，锁文件不一致先查明原因，不得直接删除。保持项目已有安装配置；不得无证据添加 --legacy-peer-deps、--force 或 --ignore-scripts；锁文件原本依赖的安装参数应保留。需要开发依赖的构建应检查 npm 版本、NODE_ENV、omit/production 配置，适用版本使用 --include=dev。--production=false 表示包含开发依赖，不能解释成排除；缺少模块时先检查声明、锁文件、实际安装树与 npm 日志，不得只换一个参数重复全量安装。安装与构建必须是不同步骤，分别记录退出和验收证据。
4. 项目构建：依赖步骤成功后，使用项目声明的构建入口作为新的独立步骤。构建失败只处理构建错误，不重新安装已经验收成功的依赖；构建成功后再执行独立、只读的产物验收。
5. 执行可观察性：安装和构建都在前台受管终端运行，保留实时输出和主命令真实退出码。不得把全部 stdout/stderr 只重定向到文件；确需留存日志时使用能够同时输出到终端且保留管道退出状态的方式。不得用 tail/head、后台任务、无条件成功分支或“set -e 后再读取 $? ”遮蔽真实结果。
6. 错误恢复：参数传递：先读取包装脚本是否转发参数。bash build.sh --legacy-peer-deps 不会自动影响内部 npm；依赖冲突证据确需此选项时，选择项目可接受的局部环境配置（如 npm_config_legacy_peer_deps=true）或经授权调整脚本内相关调用，检查全部安装入口，避免只修一处或原样重复重试。命令非零退出时先读取本次完整错误和工具自身日志，按网络/DNS/TLS、认证、运行时版本、锁文件或依赖冲突、生命周期或原生编译、权限、磁盘/inode、内存/OOM 分类，只针对已证明的原因生成一个恢复步骤。没有证据时不得切换镜像、删除锁文件、使用 force/legacy-peer-deps、修改全局 registry 或设置内存参数。镜像确有必要时优先仅作用于本次命令。
7. 长任务中断：定期复核停止或终端中断只表示没有取得真实退出结果，不等于安装或构建失败。重试前先精确检查对应进程、日志更新时间、包管理器日志、依赖目录或缓存、磁盘和内存状态；确认旧进程已结束并取得新的阻断证据后，再决定继续等待、恢复或重试，禁止原样重复执行。
8. 完成条件：依赖安装、构建和最终产物分别保留工作目录、实际入口、退出状态与独立证据。产物验收依据项目定义检查真实路径、类型、非空内容以及必要的格式、版本或最小可运行行为；仅有 exit 0、success 文本或产物目录存在不能单独完成目标。构建目标到此完成；用户目标还包括部署、启动或传输时继续对应工作，不要求先选中某个 Skill。
