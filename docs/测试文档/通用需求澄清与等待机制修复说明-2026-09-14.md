# 通用需求澄清与等待机制修复说明

日期：2026-09-14

## 本次范围

修复通用流程：模型遇到必须由用户决定的问题时，提出明确问题，并可靠等待用户提交。

没有新增容器、数据库、软件卸载等场景判断，没有新增操作授权白名单或独立 Scope 模型。领域执行方法继续由 Skill、知识库及已有执行工具提供。

## 行为变化

1. 规划明确区分两类不确定性：可安全查证的环境事实先做有限只读发现；目标选择、替代方案、授权或影响范围等用户决定缺失时，只生成 `user.request_input`。
2. 初始计划、发现后规划、阶段联合决策和调整计划中，合法且唯一待执行的澄清工具直接显示表单，不再先要求批准一个“提问计划”。
3. 等待输入、等待审批或仍在执行/校验的步骤不会被跳过；没有 `pending` 不再意味着阶段已完成。
4. 等待用户不触发自动调整倒计时、业务重拟或目标完成判断。“继续”、托管模式、旧审批按钮不能提交一个尚未回答的表单。
5. 回答绑定任务、轮次、请求 ID、执行服务器和原工具命令；取消、换轮或问题发生变化后，旧回答不能恢复当前任务。
6. 同一任务的推进、步骤执行和输入提交有在途保护；重复点击只消费一次。提交期间旧规划结果或旧失败回调不能覆盖新等待状态。
7. 用户明确提交后，恢复一次后续规划，保持原目标和约束。可继续只读取证、再次提出新的必要问题，或生成已有授权范围内的计划；不会被旧提示词强制导向变更。
8. 用户回答是新证据，不消耗自动发现展开的次数预算。业务执行仍沿用原来的审批策略。
9. 有效的未回答结构化表单可在重新打开应用后从原计划重建，并获得新的请求 ID。不恢复未提交的输入值或密钥，不自动调用模型或远程工具。
10. Skill/阶段的工具 allow-list 漏写 `user.request_input` 不再剪掉这项基础交互能力；显式禁用、显式禁止和未暴露的工具仍不放行。

## 自动化验证

新增/补充测试覆盖：

- 待输入/待审批时存在残留 `pending`，仍无远程调用、阶段验收或重拟。
- 执行或校验中的步骤阻止重复推进。
- 验证期间的旧审批无效；合法审批重复点击只执行一次。
- 普通输入及等待密钥保存期间的并发提交只生成一份回答证据。
- 过期请求、旧轮次、旧 epoch 和取消后的迟到提交无效。
- 新旧轮次的输入凭据写入按顺序处理，旧请求回滚不会越过后续输入写入。
- 阶段返回唯一澄清时直接等待，不进入业务调整事件。
- 只读目标回答后仍可生成只读计划，回答不等于批准后续执行。
- 新问题进入新表单，原问题不重复消费。
- 重新打开应用只恢复问题元数据，不恢复已输入内容、不执行工具。
- Skill 工具裁剪保留基础澄清，同时尊重显式禁止。
- Rust 现有计划、分类和联合阶段协议仍能解析澄清结果。

验证使用模拟模型与模拟连接，未对真实服务器执行变更。

## 手工复测

重启 Core，使 Rust 提示和前端流程同时生效。新建任务复测，不继续批准此前异常任务。

| 操作 | 预期 |
| --- | --- |
| 输入“检查我指定的目标状态；目标稍后由我提供，现在先向我询问” | 直接出现具体问题；未回答前不执行远程命令 |
| 暂不回答，等待并切换任务后返回 | 问题仍存在，不出现自动调整或完成总结 |
| 重复点击提交 | 只记录一次回答，只恢复一次规划 |
| 回答“目标 A，只查询，不修改” | 后续上下文包含该回答及原约束；不把填写目标解释为额外授权 |
| 新的必要问题出现后返回旧表单提交 | 旧请求不能替换新问题或改变当前任务 |
| 问题未回答时重新打开应用 | 恢复问题，但输入框为空，等待用户重新填写 |

## 日志与边界

进入澄清时记录“任务等待用户确认”，含任务、步骤、调用 ID、轮次和字段名称，不记录密钥原文。提交后继续使用既有用户输入证据与任务日志机制。

本次程序保证的是：已经进入澄清等待的任务不被错误推进、重复提交或过期响应覆盖。模型是否识别出所有语义歧义仍需要实际用例验证，不能据此宣称任意 Shell 操作均已完成授权范围验证。

原有场景业务逻辑与命令授权检查未在本次扩展。显式禁用提问工具、损坏的历史表单等情况不能凭空恢复为有效回答，应保持阻断并由用户处理。

## 补充：通用澄清单选器

`user.request_input` 新增 `select` 字段，适用于证据已经明确列出候选的目标、方案和范围选择；没有候选或需要开放回答时仍使用 `text`。这是通用表单能力，不新增数据库、容器等业务判断，也不会从历史问题的自然语言中猜测候选。

字段示例（仅在证据确实包含这些候选时使用）：

```json
{
  "key": "TARGET",
  "label": "操作目标",
  "description": "请选择本次操作的目标。",
  "type": "select",
  "required": true,
  "options": [
    { "value": "target-a", "label": "目标 A" },
    { "value": "target-b", "label": "目标 B" }
  ]
}
```

- 使用现有主题的自定义下拉框，支持鼠标和键盘操作，初始显示“请选择”，不预选第一项。
- 可选字段选过后可以清空，必填字段不提供清空入口。清空可选选择会明确记录本次未填写，不复用同名字段的历史选择。
- 每个选择字段必须提供 1 至 100 个候选，`value` 与 `label` 均为非空字符串，`value` 精确唯一；不允许默认值、预选标记或额外字段。
- 提交的是 `value` 原始字符串，而不是展示名称；不裁剪标识中的空格。前端与任务提交入口均校验是否为当前候选，空的必填项和伪造值不能继续。
- 选择目标不等于确认变更。重大操作的确认仍独立提问、显式提交，不自动同意；提交后仍遵守已有执行审批流程。
- 选项不能携带敏感信息，敏感字段继续使用 `password`。只有表单包含敏感/凭据字段时显示钥匙串保存说明。
- 等待中的结构化选项可以随计划恢复，但不恢复未提交选择、不默认采用旧回答；已提交的非敏感选择值可随任务保存。

重启 Core 后，在新任务或重新生成的问题中验证。已生成的 `text` 表单没有结构化 `options`，不会自动变为下拉框；不要为测试选择器而继续批准不希望执行的历史变更。

建议复测：

1. 输入“只向我询问要检查目标 A 还是目标 B，用选择器让我选择；现在不要执行远程命令”。应显示空的单选器，未选择前不能提交。
2. 输入“只展示一个目标选择和一个独立的操作确认问题，不执行命令”。选择目标后，独立必填确认未填写时仍不能提交。
3. 展开下拉框，用方向键选择、Esc 关闭；提交期间控件禁用，重复点击不会生成重复回答或后续计划。
4. 未回答时切换任务或重新打开应用。问题和候选保持，选择重新为空，不调用远程执行。

本补充验证：5 个选择器/澄清相关测试文件共 123 项通过；Rust 121 项通过、2 项 live 测试忽略。类型检查、生产构建和 `git diff --check` 通过。完整前端回归仍有上述模型高级参数、知识上传界面的 4 项既有失败；本次未修改这些失败用例或调用真实服务器。
