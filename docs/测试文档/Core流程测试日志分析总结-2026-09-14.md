# Core 流程测试日志分析总结

分析日期：2026-09-14。范围：文档中标记的 11 个任务、对应三类任务日志、日志索引、系统连接事件以及相关当前源码。

## 1. 结论

本轮不能判定为“全部通过”。基础执行、重复文件保护、双服务器后台执行有成功证据，但发现以下需要优先处理的问题：

1. **P0：目标语义越界。** 请求重启 Java 服务，在没有发现 Java 服务后，实际重启两个 Docker 业务容器，并通过完成门禁。对象存在、命令成功不等于用户目标正确。
2. **P1：日志过度脱敏。** 时间戳、命令数字、JSON 字段名和嵌套证据 ID 被替换，部分 detail 字符串已无法再次作为 JSON 解析。
3. **P1：断网恢复停在执行通道等待。** 第二条追加命令已有两行输出与 exit 0，但后续校验缺失；服务器恢复与任务 Agent 执行通道恢复不是同一件事。
4. **P1：后台任务返回后丢失当前视图。** 切回服务器清空 activeTaskId，有直接源码依据；任务本身并未因此停止。
5. **P1：计划依赖与环境兼容性不足。** 延迟就绪最终成功，但发生多次缺前置文件、启动参数不兼容及无效轮询，累计 30 次模型请求。
6. **P1：结构化观察误判。** `java_process_count=0` 被 process 适配器当作存在进程的证据。

这些问题主要发生在编排、目标校验、恢复和可观测性层面，不能简单归因于模型接口失败：本次所查 11 个任务的 model-calls 共记录 **87 次请求及 87 次 HTTP 200 响应**。HTTP 成功不等于计划有效或任务正确完成。

## 4. 主要问题与证据

### 4.1 P0：没有 Java 服务，却重启其他业务容器

任务：`task-1789380823298-8bzpnt`。

- `M:26` 的计划已经将执行对象改为 `stock-datahub` 和 `TickFlow_Stock_Panel`，使用 `docker restart`。
- `E:41` 包含该命令实际执行记录；`E:42` 包含后置 inspect 输出，两容器均为 running，其中一个 health=starting。
- `M:28`、`M:30` 用“业务后端容器重启成功”证明“Java 服务重启完成”。
- `M:32` 的最终总结又承认没有对应的 Java 服务，表示如果真实目标并非这两个容器再告知。

**问题不是单纯措辞错误，而是对象语义发生变化后仍允许执行并通过验收。** 文档要求该场景只测试到澄清／确认，不批准真实重启；日志有“计划已批准”，但不能由此还原是用户手动批准还是托管模式自动批准，也不能证明用户明确同意将 Java 服务替换成这两个容器。因此不能断言完全没有任何审批，能够确认的是日志缺少足以支持对象替代的明确用户确认。

建议：把目标对象、对象类型、允许变更范围做成不可由模型复核自行扩大的约束。无 Java 候选时返回“未找到目标”；多个候选时进入澄清；替换成容器必须重新获得明确授权。`running` 只证明进程状态，不自动等于业务健康；`health=starting` 应标记尚未就绪，不能与 healthy 混同。

另一任务 `task-1789380688264-g0ruc3` 的 `E:14–17` 仍在尝试重启／调整，未形成目标澄清后停止的闭环；没有最终完成事件，不能猜测后来是否被用户结束。

### 4.2 P1：脱敏破坏日志结构与事实

多个任务的 E 记录中，`createdAt` 中的数字被替换；命令中的参数、退出码、进程计数也被替换。Java 用例 `E:8` 的嵌套 processCount 数值被替换，`E:10` 中字段名也出现替换痕迹。系统连接事件同样受影响。

源码依据：`src/stores/ops.ts` 的 addLog 对事件字符串字段调用 redactExecutionOutput；`src/features/agent/secretTool.ts` 使用所有已知 secret 的 `split(secret).join(...)` 全局替换，没有短值边界限制。开发者日志也有全局精确字符串替换路径。

**推断**：短值或普通词被作为敏感值后匹配到了普通数字／文本；本次没有读取或披露凭据，不能确定是哪条敏感配置触发。顶层 taskId 等关联字段会由日志 writer 的 context 回填，因此目录索引仍可关联，但嵌套内容并不会全部修复。

建议：对结构化字段按 schema 脱敏，保留时间、枚举、计数、退出码及关联 ID；正文中的短敏感值采用字段／上下文约束，不能简单取消保护。记录规则版本与替换数量，不记录敏感原文。已有被替换的信息通常不可从该日志恢复，可用仍完整的模型请求上下文交叉核对，但不能把猜测值写回原日志。

### 4.3 P1：断网后服务器已连上，任务执行通道仍等待

任务：`task-1789381296314-nvvj2d`。

- `E:4–6`：创建目录、首行写入及校验完成。
- `E:7`：等待后的第二次追加记录，输出中有两行时间和 `[exit: 0]`。因此不能说“第二步命令必然失败”，也不能声称只有一行写入。
- 后续没有第三步读取、第二步独立校验或任务完成记录。M 只有需求理解与计划生成两次调用。
- `system/events.jsonl:242、244、251、252` 属于同一 serverId，最后一条为 connected；文档同时报告持续等待以及点击“检查终端恢复”后重复等待。

源码依据：`ops.ts::adjustmentTargetState` 读取 `useAgentTerminalStore().sessionsByTask[task.id]`；`waitForAdjustmentTransportRecovery` 在存在 session ID 时要求 Agent session 为 ready 且非 busy，不能仅凭服务器 connected 放行。等待循环为 120 × 250ms，超时转为手动恢复。相关提示通过 pushMessage/persist 写入任务状态，当前这份文件日志没有对应完整恢复事件。

**结论**：恢复条件分层和事件缺口已确认；具体是旧代次会话未重建、状态未同步还是其他通道问题，缺少 session 状态轨迹，尚不能唯一定位。不能为了消除等待而把 server connected 直接当作 Agent ready。

建议：记录 server generation、Agent session ID/generation、状态转换、恢复触发原因；提供明确的 Agent 通道重建路径。区分“主命令已成功、仅校验待恢复”和“主命令是否执行未知”，前者恢复只读校验，后者先取证再人工决定，禁止盲目重放追加命令。本次没有恢复后的远程文件快照，不能证明绝无重复写入。

### 4.4 P1：切回服务器清空任务视图；缺少任务运行指示

任务：`task-1789381005305-agfyet`、`task-1789381010281-wvhf83`。

两任务均有 `E:10` 完成事件，M 中 serverId 分别为 `srv-1787131764330-rlbu0t`、`srv-1787124713205-3e747a`。A 的模型事件时间范围为北京时间 18:16:45–18:17:16，B 为 18:16:50–18:16:56，支持二者交叠执行。文档实测明确记录“继续运行、记录完整、未混入、没有重连蒙板”。这不能替代所有 UI 状态隔离测试，但当前样本没有任务串服务器的证据。

`src/components/AgentConsole.vue:48` 附近对 props.active 的 watch 在激活时无条件清空 activeTaskId，直接解释“切回来到了首页”。这也是把“从服务器管理首次进入新任务”的需求过度应用到了“已有工作台标签间切换”。

建议：首次入口与标签恢复分开处理。首次进入可显示新任务，标签切回保留该服务器当前选择；删除任务后才切新任务。标签增加独立的 Agent 运行／等待审批／异常指示，不复用 SSH 绿点。文档中的运行指示缺失属于 UI 需求，不应误判为连接失败。

### 4.5 P1：延迟就绪的失败主要来自依赖缺失与参数不兼容

任务：`task-1789380401237-a4xykn`。

- `D:2–3`：计划被校验拒绝，涉及后台进程脱离跟踪、observe 步骤配置 validation。
- `M:10`：模型已经指出 `.last_delay_workdir` 尚未创建，却返回 continue；实际后续进入了依赖该文件的轮询，`M:12` 确认此前置失败。
- `E:18`：`systemd-run` 不支持 `--wait`；`E:32`：不支持 `--no-block`。失败启动后仍有轮询超时。
- `E:52` 最终输出 `content=ready`、`READY_CONTENT_OK`，`M:60` 汇总最终成功及早期兼容性失败。
- 模型调用跨度 10:06:41.282Z–10:10:38.269Z，约 237 秒，30 次请求。这是从首个模型请求至最后响应的跨度，不是单个命令运行时间，也不等于单次轮询窗口。

因此，本例不是“第一次文件不存在就过早校验失败”；系统实际上进行了有界轮询，主要浪费在未满足前置条件和启动命令不兼容。最终成功应保留，但质量评定不能仅看 completed。

建议：执行计划显式声明依赖及产物，启动失败时阻止依赖步骤；continue 不应被解释为“需要修复但照原计划继续”。先检测工具版本／选项再生成命令；相同失败指纹不得重复使用失效选项。通用后台进程跟踪约束要有可用的受管执行方案，不能反复要求模型在相互冲突的规则中试错。

### 4.6 P1：process 观察器把“计数为 0”识别为有进程

任务 `task-1789373391836-spdv5c`：`E:7` 输出 `java_process_count=0`；紧接着 `E:8` 却记录 processFound=true、observationStatus=matched。日志中的 processCount 被脱敏，不能据此还原具体原始数值。

源码 `src/features/skills/validationAdapters.ts` 的 found 基于非空输出判断，process 分支在没有 PID 时仍至少给出一个计数。说明适配器不能把任意非空文字当成进程列表。

最终任务总结识别了没有 Java 服务，未因此直接宣布有服务，但错误结构化事实会影响其他复核和知识提炼。建议区分 PID 列表、计数标记、自然语言输出；对 count=0 明确 not_found，并添加证据冲突检测。

## 6. 修改优先级与回归验收

| 顺序 | 修改项 | 验收标准 |
|---|---|---|
| 1 | 目标对象与审批约束 | Java 不存在且有非 Java 容器时，只澄清／停止；不重启容器；目标变化必须重新确认 |
| 2 | 结构化日志脱敏 | 日期、数字、退出码、关联 ID、JSON key 保真；敏感字段仍被保护；包括短敏感值回归 |
| 3 | Agent 通道恢复与恢复审计 | 服务器恢复后 Agent 会话有明确 ready／失败结果；追加命令已成功则仅补校验；未知结果不自动重放 |
| 4 | 激活视图与标签任务状态 | A 运行时切 B 再回 A 保留任务；首次入口／删除后显示新任务；任务状态独立于 SSH 状态 |
| 5 | 依赖、版本探测与复核决策 | 写入未启动不进入轮询；不重复失效参数；20 秒轮询上限明确且用单调时钟验证 |
| 6 | 观察器语义 | count=0 判 not_found，真实 PID 列表才给进程计数；内容和结构化结果冲突时不得无条件完成 |
| 7 | 补足测试证据 | 差异文件不覆盖、连续需求录屏、断网后文件行数、上传前后对照、失败前任务 ID |

本报告仅分析并生成文档，没有实施上述修改，也没有对服务器恢复后的文件或业务健康作未验证的保证。后续优先修复 P0，再重跑模糊目标用例；不要在真实业务环境重复容器重启测试。
