# Opsark 步骤校验与证据链优化方案

> 文档状态：首个核心迭代已实施，后续阶段持续推进  
> 编制日期：2026-07-30  
> 适用范围：智能需求处理控制台的计划执行、步骤校验、异常处理、模型复核与结果总结

## 当前实施进度

截至 2026-07-30，首个核心迭代已经落地：

- 已增加执行状态、观察状态、步骤结果和执行证据数据结构。
- 已实现进程、端口归属、HTTP、SQL、服务、文件、Docker、日志和通用命令校验器的兼容式识别。
- 旧计划仍可继续使用原有 `validation` 字段，程序会自动补齐校验器。
- 正常证据一致的步骤不再调用模型复核。
- 只有证据无法解析或主命令与独立校验冲突时才调用一次异常模型复核。
- `not_found`、`unhealthy` 和 `warning` 已作为有效观察状态与执行失败分离。
- 当前计划、历史计划和多轮上下文会保存结构化步骤结果与证据摘要。
- 执行卡片已展示执行状态、观察状态、结构化事实和异常提示。
- 前端项目部署计划会在依赖安装前自动补充运行时精确检查，从 package.json 和 package-lock 中读取 Node.js/Vite engines。
- `TOO_OLD`、`EBADENGINE` 和构建工具版本要求会被识别为阻断型证据；剩余计划没有运行时修复步骤时禁止继续安装或构建。
- 依赖漏洞和非阻断警告会进入观察结果及最终总结，但不会与命令执行失败混淆。
- 已知构建失败会提取运行时不兼容、磁盘不足、权限、命令缺失或仓库 404 等根因。
- `本轮结果总结` 只在整个任务完成、失败结束、取消或用户终止后展示；步骤失败等待调整时单独展示暂停原因。

尚未完成的主要内容：

- 通用条件步骤协议和自动分支跳过。
- 独立的全局证据仓库及证据引用界面。
- 更完整的 Nginx、Docker 和日志专用解析器。
- 基于证据过期时间的选择性复查。
- 局部调整步骤的依赖图裁剪。

## 1. 背景

当前核心流程为：

```text
模型生成计划
→ 用户审批
→ 执行当前步骤
→ 执行 validation 命令
→ 每一步调用模型复核
→ 继续、调整或完成
```

该方案已经能够形成完整业务闭环，但在真实运维场景中暴露出以下问题：

- 命令执行成功与业务目标满足没有完全分离。
- `grep` 无匹配、资源不存在、端口未监听等有效诊断状态容易被当作步骤失败。
- 模型可以生成语义不准确或与主命令重复的 `validation` Shell。
- 每一步都调用模型复核，增加等待时间和 Token 消耗。
- 模型看到单条 `ERROR`、版本偏低或依赖不存在时，可能过早要求重新生成计划。
- 调整计划容易重复已经完成的检查，导致计划不断膨胀。
- 原始终端文本缺少结构化事实，模型容易把普通监听端口错误归属到目标项目。
- 最终总结可能引用未经验证的端口、访问地址或推测性根因。

本次优化借鉴 Codex 的“执行、观察、验证、迭代”方式，但保留 Opsark 面向服务器运维所必需的计划审批、风险控制和审计能力。

## 2. 优化目标

将步骤处理流程调整为：

```text
模型一次生成精简计划
→ 用户按风险审批
→ 执行步骤
→ 程序收集并结构化证据
→ 确定性规则判断执行与观察结果
→ 正常状态直接继续
→ 证据冲突或无法解释时才调用模型
→ 必要时生成一次局部调整
→ 全部结束后根据证据生成总结
```

核心目标：

1. 程序负责确定性事实，模型负责语义理解和少量异常分析。
2. 不再把“未发现目标”直接等同于“命令执行失败”。
3. 普通步骤不再强制调用模型复核。
4. 所有结论都能追溯到命令输出或结构化证据。
5. 调整计划只修改受影响部分，不推翻已经验证的步骤。
6. 未经验证的端口、URL、进程归属和日志根因不得进入确定性总结。

## 3. 设计原则

### 3.1 执行成功不等于目标满足

每一步至少区分两类状态：

```text
执行状态：命令是否正常执行
观察状态：命令观察到的业务状态是什么
```

例如查询数据库 `ffp`：

```text
查询命令执行成功
executionStatus = success

查询结果不存在 ffp
observationStatus = not_found
```

这代表状态检查成功，应继续创建数据库，而不是暂停任务。

### 3.2 证据优先于模型判断

模型不得直接覆盖以下程序事实：

- SSH 命令退出状态。
- 用户终止状态。
- 安全策略拦截。
- 用户审批结果。
- 可解析的 HTTP 状态码。
- 可解析的 PID、端口归属、SQL 查询值和文件属性。

模型可以解释这些事实，但不能虚构或修改事实。

### 3.3 正常路径不调用模型

步骤满足以下条件时直接继续：

- 主命令执行成功。
- 校验器获得可解析证据。
- 观察状态属于步骤声明的有效状态。
- 证据之间没有冲突。

只有证据冲突、输出不可解析或剩余计划无法处理异常时，才调用模型复核。

### 3.4 诊断发现异常不等于步骤失败

以下结果通常属于有效诊断状态：

- 没有匹配的进程。
- 资源不存在。
- 服务处于 inactive。
- 端口没有监听。
- HTTP 返回非 2xx。
- 日志中发现 `WARN` 或 `ERROR`。
- 软件版本低于要求。

只有诊断命令本身无法执行、输出无法解析或连接失败时，才属于执行或证据失败。

## 4. 目标数据模型

### 4.1 步骤执行结果

```ts
type ExecutionStatus =
  | "success"
  | "failed"
  | "cancelled"
  | "blocked";

type ObservationStatus =
  | "matched"
  | "not_found"
  | "healthy"
  | "unhealthy"
  | "warning"
  | "unknown";

interface StepResult {
  executionStatus: ExecutionStatus;
  observationStatus: ObservationStatus;
  exitCode?: number;
  facts: Record<string, unknown>;
  warnings: string[];
  evidenceIds: string[];
  failureReason?: string;
}
```

### 4.2 结构化校验定义

```ts
type ValidatorType =
  | "command"
  | "process"
  | "service"
  | "port-owner"
  | "http"
  | "file"
  | "sql-query"
  | "docker"
  | "log";

interface StepValidation {
  type: ValidatorType;
  command: string;
  assertions: ValidationAssertion[];
  validStates: ObservationStatus[];
}

interface ValidationAssertion {
  field: string;
  operator:
    | "exists"
    | "equals"
    | "not_equals"
    | "contains"
    | "matches"
    | "greater_than"
    | "less_than";
  value?: string | number | boolean;
}
```

### 4.3 条件步骤

```ts
interface StepCondition {
  stepId: string;
  field: string;
  operator: "equals" | "not_equals" | "exists";
  value?: string | number | boolean;
}
```

示例：

```json
{
  "title": "创建 ffp 数据库",
  "condition": {
    "stepId": "check-ffp",
    "field": "facts.exists",
    "operator": "equals",
    "value": false
  }
}
```

如果数据库已经存在，该步骤由程序标记为 `skipped`，不再请求模型判断。

### 4.4 证据对象

```ts
interface ExecutionEvidence {
  id: string;
  taskId: string;
  stepId: string;
  type: ValidatorType | "command-output";
  source: string;
  facts: Record<string, unknown>;
  rawOutput: string;
  collectedAt: string;
}
```

模型总结优先读取 `facts`，只有需要进一步解释时才读取已脱敏的 `rawOutput`。

## 5. 模型与程序的职责边界

| 能力 | 程序负责 | 模型负责 |
|---|---:|---:|
| 命令退出码、超时、取消 | 是 | 否 |
| 风险策略和审批 | 是 | 否 |
| PID、端口、HTTP、SQL 等结构化解析 | 是 | 否 |
| 判断证据是否可解析 | 是 | 否 |
| 按条件跳过步骤 | 是 | 否 |
| 理解用户自然语言目标 | 否 | 是 |
| 首次生成精简计划 | 否 | 是 |
| 解释多项证据之间的业务含义 | 部分 | 是 |
| 处理无法结构化的异常 | 部分 | 是 |
| 生成面向用户的最终总结 | 提供事实 | 是 |
| 覆盖程序失败或安全拦截 | 否 | 否 |

## 6. 分阶段实施计划

### 阶段一：执行状态与观察状态解耦

### 目标

先解决“查询结果不符合目标就被判执行失败”的核心问题，不大幅改变现有界面和模型协议。

### 改造内容

- 为 `PlanStep` 增加 `result` 字段。
- 引入 `executionStatus`、`observationStatus`、`facts` 和 `warnings`。
- 将主命令退出码判断与业务状态判断拆开。
- 将 `grep` 无匹配、资源不存在、服务 inactive 等归类为有效观察状态。
- 保留现有 `validation` 字段作为兼容入口。
- 日志卡片同时展示“执行状态”和“观察结果”。

### 主要涉及文件

- `src/types.ts`
- `src/stores/ops.ts`
- `src/services/backend.ts`
- `src-tauri/src/lib.rs`
- `src/components/AgentConsole.vue`

### 验收标准

- 查询不存在的数据库不会被标记为命令失败。
- 查询不到 Java 进程时任务可以正常完成并总结“未发现”。
- 服务 inactive 可以作为诊断结果进入后续步骤。
- 真正的连接失败、命令不存在和权限不足仍然会暂停。
- 原有任务数据可以正常加载。

### 阶段二：减少逐步骤模型复核

### 目标

降低等待时间、Token 消耗和模型过早重规划的概率。

### 改造内容

- 移除正常步骤后的强制 `reviewStep()` 调用。
- 程序校验通过且证据一致时直接执行下一步。
- 仅在以下情况调用模型复核：
  - 证据互相矛盾。
  - 输出无法解析。
  - validation 失败但可能属于正常业务分支。
  - 当前异常不在剩余计划覆盖范围。
  - 所有步骤结束，需要生成总结。
- 模型复核失败或超时时，保留程序事实，不自动推翻计划。
- 审计日志记录模型被调用的具体原因。

### 验收标准

- 普通三步骤查询任务只调用一次需求规划和一次最终总结模型。
- 正常步骤之间无额外模型等待。
- 单条日志 `ERROR` 不再直接触发调整计划。
- 模型不可用时，确定性校验任务仍可完成。
- 模型调用次数、耗时和失败原因可在日志中查看。

### 阶段三：结构化校验器注册表

### 目标

逐步替代容易产生歧义的任意 Shell `validation`，让常见运维对象由程序解析。

### 首批校验器

1. `ProcessVerifier`
   - 解析 PID、命令行、用户、启动时间和资源占用。
2. `ServiceVerifier`
   - 解析 systemd/service 状态及失败原因。
3. `PortOwnerVerifier`
   - 建立端口到 PID、进程或容器的归属关系。
4. `HttpVerifier`
   - 解析状态码、重定向、标题、内容特征和请求耗时。
5. `SqlQueryVerifier`
   - 解析列名、行数据、计数和资源存在状态。
6. `FileVerifier`
   - 解析存在状态、权限、属主、大小、时间和校验和。

### 后续校验器

- `DockerVerifier`
- `LogVerifier`
- `NginxVerifier`
- `PackageVerifier`

### 实现要求

- 模型只选择校验器和参数，不负责定义所有解析规则。
- 每个校验器返回统一 `StepResult`。
- 校验器必须只读。
- 原始输出必须脱敏并进入审计日志。
- 未识别类型回退到兼容的 `command` 校验器。

### 验收标准

- 端口监听不能在没有 PID、容器或代理证据时归属到目标项目。
- HTTP 访问地址只有在实际请求后才能标记为已验证。
- SQL 查询无记录与 SQL 执行失败可以明确区分。
- 日志出现错误被记录为 `warning` 或 `unhealthy`，但不直接等同于执行失败。

### 阶段四：证据链与条件步骤

### 目标

让计划执行依赖程序事实推进，减少模型参与简单分支判断。

### 改造内容

- 增加 `ExecutionEvidence` 存储。
- 每一步保存结构化事实及原始输出引用。
- `PlanStep` 支持 `condition`。
- 执行前由程序判断条件：
  - 条件满足：执行。
  - 条件不满足：标记 `skipped`。
  - 依赖证据缺失：进入异常分析。
- 最终总结输入改为“结构化事实 + 必要原始输出”。
- 历史任务保存证据链，供同一任务下一轮需求复用。

### 验收标准

- 数据库已存在时自动跳过创建步骤。
- 服务已经处于目标状态时自动跳过重启步骤。
- 后续询问“如何访问”可以读取上一轮已验证 URL。
- 每条总结结论可以定位到对应步骤和证据。
- 未验证地址必须明确标记为“尚未验证”。

### 阶段五：局部调整与异常恢复

### 目标

避免失败后重新生成完整计划，控制计划长度和执行范围。

### 改造内容

- 保留所有已完成步骤和证据。
- 只把失败步骤、剩余步骤和相关证据交给模型。
- 调整计划最多生成 1～3 个替代步骤。
- 每轮最多自动调整一次。
- 不允许重新执行已经确认的前置检查，除非证据已经过期。
- 变更类调整仍受原有风险审批规则控制。
- 下载、编译等长命令支持持续输出、耗时提示和用户终止。

### 验收标准

- 单步失败不会扩张为十几个新步骤。
- 调整计划不会重复已完成的 Java、Maven、Git 等检查。
- 已完成步骤及输出不会丢失。
- 调整达到上限后明确停止并说明需要什么人工输入。

### 阶段六：界面与可观测性完善

### 目标

让用户能够快速理解“做了什么、看到了什么、为什么继续”。

### 改造内容

- 计划卡片展示步骤目标、风险和执行条件。
- 执行记录卡片展示：
  - 执行状态。
  - 观察状态。
  - 结构化事实。
  - 原始输出下拉详情。
- 总结卡片展示关键结论及证据来源。
- 模型日志展示调用原因、耗时和决策。
- 长任务展示运行时间、最近输出时间和终止按钮。
- 对 `not_found`、`warning`、`failed` 使用不同视觉语义。

### 验收标准

- “没有匹配数据”不会使用失败样式。
- 用户能从卡片看出端口归属证据。
- 用户能区分程序校验、模型分析和最终总结。
- 原始命令输出仍可完整查看并保持脱敏。

## 7. O2OA 场景示例

用户需求：

```text
检查 O2OA 这个项目的运行情况
```

推荐计划：

### 步骤一：确认目标进程

收集：

```json
{
  "processFound": true,
  "pid": 5149,
  "command": "/opt/O2OA/o2server/start_opsark.sh"
}
```

### 步骤二：确认端口归属

收集：

```json
{
  "listeners": [
    {
      "port": 8088,
      "pid": 5149,
      "owner": "java"
    }
  ]
}
```

不能因为 8080 由 Docker proxy 监听，就直接说 8080 属于 O2OA。

### 步骤三：确认代理链

收集 Nginx `server_name`、`location` 和 `upstream`，建立：

```text
外部 80
→ Nginx 配置
→ 127.0.0.1:8088
→ O2OA PID 5149
```

### 步骤四：验证页面

收集：

```json
{
  "url": "http://server.example/",
  "httpStatus": 200,
  "pageIdentified": true,
  "title": "O2OA"
}
```

只有取得这组证据后，才能总结“页面地址已经验证可访问”。

### 步骤五：检查日志

如果发现：

```text
127.0.0.1:7080 ... Connection refused
```

应记录为：

```json
{
  "observationStatus": "warning",
  "facts": {
    "dependency": "127.0.0.1:7080",
    "connection": "refused"
  },
  "warnings": [
    "发现依赖连接失败，但尚未证明它位于页面主请求链路"
  ]
}
```

该步骤执行成功，继续完成其余只读诊断；只有建立请求链路关联后，才能把它认定为根因。

## 8. 测试计划

### 单元测试

- 命令退出码与观察状态映射。
- `grep` 无匹配的正常分支。
- SQL 资源存在与不存在分支。
- 条件步骤执行和跳过。
- HTTP、端口和进程证据解析。
- 模型复核触发条件。
- 调整次数和替代步骤数量限制。

### 状态机测试

- 正常查询任务不调用逐步骤模型复核。
- 诊断异常后继续剩余只读步骤。
- 主命令失败后正确暂停。
- 用户终止后停止当前远程进程及后续步骤。
- 模型不可用时使用程序证据完成任务。

### 场景回归测试

- 查询不存在的 Java 进程。
- 查询、创建和复查 MySQL 数据库。
- 检查 O2OA 进程、端口和页面。
- 页面空白时只读诊断，不擅自重启。
- 日志中出现不相关 ERROR 时不立即重规划。
- 下载或编译长时间运行时保持输出和可终止状态。

### 构建验收

```bash
npm test -- --run
npm run build
cargo test --manifest-path src-tauri/Cargo.toml --lib
cargo check --manifest-path src-tauri/Cargo.toml
npm run tauri build -- --debug --bundles app
```

## 9. 迁移与兼容策略

- 第一阶段保留现有 `expected` 和 `validation` 字段。
- 新增字段全部设置为可选，避免旧任务无法反序列化。
- 旧步骤由兼容适配器生成基础 `StepResult`。
- 新模型返回结构化校验时使用新流程。
- 模型仍返回旧格式时回退到 `command` 校验器。
- 历史输出继续保留，不进行破坏性迁移。
- 稳定后再逐步降低任意 Shell validation 的使用比例。

## 10. 优先级建议

| 优先级 | 内容 | 预期收益 |
|---|---|---|
| P0 | 执行状态与观察状态解耦 | 解决正常业务分支误判失败 |
| P0 | 正常步骤取消模型复核 | 降低延迟和 Token 消耗 |
| P0 | 进程、端口、HTTP、SQL 校验器 | 覆盖主要真实运维场景 |
| P1 | 证据对象与条件步骤 | 减少模型分支判断 |
| P1 | 局部调整计划 | 避免计划反复膨胀 |
| P1 | 证据链总结 | 防止总结虚构或错误归属 |
| P2 | Docker、Nginx、日志校验器 | 加强复杂部署诊断 |
| P2 | 证据可视化和性能指标 | 提升可读性和可维护性 |

## 11. 建议的首个迭代范围

首个迭代建议只完成以下内容：

1. 为步骤增加 `StepResult`。
2. 区分 `executionStatus` 和 `observationStatus`。
3. 正常步骤不再调用模型复核。
4. 实现 `ProcessVerifier`、`PortOwnerVerifier`、`HttpVerifier` 和 `SqlQueryVerifier`。
5. 仅在证据冲突、输出无法解析或计划无法继续时调用模型。
6. 保留一次局部调整上限。
7. 增加数据库、进程、端口和页面空白场景的回归测试。

完成这一迭代后，再进入条件步骤和完整证据链建设，可以在不大幅重构现有界面的情况下获得主要收益。

## 12. 通用部署流程的第二阶段优化

新一轮跨项目测试表明，仅把“执行状态”和“观察状态”拆开还不够。运行时安装器可能退出 0，但下载的二进制仍可能因为宿主机的 OS、架构、glibc 或 C++ ABI 过旧而无法启动。因此，部署和复杂修复任务统一采用以下有界流程：

```text
理解用户目标
  → 生成只读发现步骤
  → 执行并形成结构化证据
  → 在第一个环境敏感变更前细化一次后续计划
  → 用户审批或自动模式继续
  → 执行变更
  → 程序校验后置条件
  → 仅在未知或冲突证据时调用模型复核
  → 完成总结，或最多一次失败调整
```

### 12.1 只读发现阶段

代码部署、运行时升级和构建环境修复至少采集：

- 仓库文档、清单、锁文件、构建脚本与精确运行时要求。
- 操作系统 ID 和版本、CPU 架构、libc 版本。
- libstdc++ 可提供的最高 `GLIBCXX`、`CXXABI` 符号。
- 当前运行时、包管理器，以及 Docker/Podman 等隔离能力。

这些步骤只收集事实，不安装依赖、不切换默认运行时、不重载服务。

### 12.2 一次计划细化

完成平台发现后、执行第一个环境敏感变更前，允许模型依据真实证据细化一次剩余计划：

- 已完成的发现步骤和卡片原样保留。
- 新计划只包含尚未执行的变更和最终验收，最多 6 步。
- 计划细化不计入失败调整次数。
- `discoveryRefined` 防止重复细化和循环调用模型。
- 安全模式重新请求用户批准；自动模式继续执行。

这一步不是失败重规划。它把最初基于有限上下文的候选计划，转换为基于真实平台事实的可执行计划。

### 12.3 运行时与平台兼容门禁

- 校验器按步骤语义和独立校验命令分类，不能因为复合命令中偶然包含 `curl` 就识别成 HTTP。
- 远程 `curl | bash` 安装脚本不是默认可接受方案。
- 新运行时必须先在同一主机实际执行并验证版本与 ABI，再切换全局默认值。
- 识别 `GLIBC_* not found`、`GLIBCXX_* not found`、`CXXABI_* not found`、ELF 架构错误等硬阻断。
- 宿主机不兼容时选择兼容容器或隔离构建环境，不自动升级系统 libc/libstdc++。

### 12.4 执行与后置条件分别呈现

主命令退出 0、独立校验失败时：

- `executionStatus = success`，表示命令本身已完成。
- `observationStatus = unhealthy` 或 `unknown`，表示目标状态未达成。
- 整个步骤先不被程序接受，进入一次异常模型复核。
- 复核后只有满足安全边界时才继续，否则任务暂停。
- 界面显示“执行成功 / 状态异常”，并分别保留模型意见与程序最终决策。

这样能够准确表达“安装器成功，但新程序无法运行”，避免把问题错误归类成 SSH 或 Shell 执行失败。

### 12.5 长输出压缩

下载和构建仍实时显示，但持久化证据会压缩连续的回车覆盖进度帧，仅保留最终进度及业务输出。该策略减少卡片渲染、持久化和模型上下文体积，不影响最终错误、校验输出和退出码。

## 13. 发现语义与计划规范化补强

针对“清单读取成功，但可选字段不存在导致任务暂停”的测试场景，增加以下通用规则：

- 发现步骤的校验只证明文件可读、结构可解析和证据可获得，不能强制要求可选字段存在。
- `package.json` 未声明 `engines` 时记录 `requiredNode=unspecified`，继续读取锁文件中实际构建工具的要求。
- 模型已经生成清单或运行时检查时，程序将其升级为结构化检查，不再重复插入相同语义的步骤。
- 只读运行时探测返回“版本不匹配”属于有效观察，不改写成命令执行失败。
- 平台探测只接受数字格式的 `GLIBCXX_x.y.z` 与 `CXXABI_x.y.z`，排除普通符号名称。
- 普通配置弃用提示只保留在证据详情中，不提升步骤异常等级。
- 用户没有明确要求清理时，规范化层移除模型无证据生成的 `rm -rf` 残留清理步骤。
- 计划进度将 `failed` 计入“已处理”，确保已执行但未通过的步骤不会少计。

## 14. 调整恢复与独立 Shell 约束

- 一次调整上限属于“当前需求轮次”，不是整个任务会话；用户在同一任务发送新需求时，重置 `adjustmentCount`、发现细化和终止标志。
- 任务暂停后输入“进行调整”“重新调整”或“重试”，直接触发当前轮次的调整动作，不再交给模型误判为咨询。
- 已确认的运行时阻断可以继续后续只读发现，但在进入依赖安装或构建前必须被真实修复步骤解决并验证。
- `curl | bash` 等远程安装脚本属于变更操作；即使管道最终退出码为 0，只要输出出现连接重置、DNS、超时等网络错误且后置校验失败，任务立即暂停。
- 每个远程步骤运行在独立非交互 Shell 中。`source`、`export`、`cd`、alias 和 PATH 修改不会跨步骤继承，使用 nvm 等工具的命令和校验必须自行加载环境。

## 15. 辅助计划细化的降级策略

发现阶段后的计划细化是优化步骤，不是业务执行的硬依赖：

- 模型返回的细化计划无法解析时，自动追加严格 JSON 约束重试一次。
- 连续两次解析失败时，保留已经由用户或自动模式批准的原计划继续执行。
- 回退只写入过程记录和模型警告日志，不设置 `needs_adjustment`，不占用本轮调整次数。
- 原计划仍然受风险审批、运行时阻断、程序校验和终止机制保护。
- 只有真正的主命令失败、后置条件失败或未解决硬阻断才能暂停业务。

## 16. 瞬时校验冲突与人工恢复入口

- HTTP、网络等瞬时只读检查中，主命令已得到明确结构化结果而独立校验不一致时，自动重试独立校验一次。
- 重试仍不一致时保留“主结果成功 + 证据冲突”，进入异常复核，不直接改写为执行失败。
- HTTP 校验中的退出码 1、22、28可作为只读状态证据；退出码 127 等命令不可用状态仍属于校验失败。
- 相同计划内模型平台检查与程序结构化平台检查自动去重，优先保留已完成步骤，其次保留带 `OPSARK_PLATFORM_CHECK` 的结构化步骤。
- 自动调整仍限制一次，但达到上限后界面提供“再次生成解决方案”；只有用户明确点击或输入调整指令才开启新的人工调整周期，避免后台自动循环。

## 17. 执行异常的一次模型复核

执行链统一调整为：

```text
主命令执行
  → 主命令失败：保留失败事实并调用模型复核一次
      → 结合用户原始约束、完整计划、执行历史和剩余步骤
      → 程序安全门禁裁决继续或调整
  → 运行时前置条件不满足：在安装或构建前调用模型复核一次
      → 结构化约束允许 best_effort 且模型判定符合约束：保留风险继续
      → 模型不可用或判定违反约束：暂停并调整计划
  → 程序后置校验
  → 校验通过：按确定性规则继续
  → 校验失败但主命令成功：调用模型复核一次
      → 程序安全门禁裁决
      → 继续 / 调整 / 只读目标已完成
```

具体约束：

- 模型同时接收原始用户目标与约束、完整计划、主命令证据、后置校验证据、已完成执行记录和剩余步骤。
- 每个失败步骤最多调用模型复核一次，不因复核意见再次生成计划或循环复核。
- 模型只能决定工作流继续、调整或结束，不能把真实的命令失败改写为执行成功。
- 需求理解模型输出并持久化 `changePolicy`、`environmentPolicy`、`failurePolicy`、`prohibitedActions`、`requiredConditions`、`userDirectives`，后续流程不再用中文关键词判断授权。
- 结构化执行约束优先于模型先前生成的计划；剩余计划违反约束时应调整。
- 运行时发现步骤成功但观察到版本不兼容，不代表工作流必须立即暂停；在依赖安装或构建前应结合用户要求复核。
- 当 `failurePolicy=best_effort`、当前步骤符合环境与变更策略、且模型返回 `continue` 时，程序允许一次真实尝试并保留风险；后续仍以真实退出码和证据为准。
- 模型不可用或没有返回 `continue` 时，运行时门禁继续阻止安装和构建。
- 主命令失败后，只有只读诊断已经取得用户需要的有效状态，或者剩余计划明确包含对应恢复路径时才允许继续。
- 构建、部署和变更命令失败后不能直接判定任务完成；没有恢复步骤时必须调整。
- 模型不可用或返回规则兜底结果时，执行失败或后置校验失败不得自动继续。
- 只读步骤在主输出明确、独立校验可能受瞬时网络或表达式影响时，模型可以决定继续或完成。
- 变更步骤不能在后置条件失败时直接完成；仅当模型建议继续且剩余计划明确包含加载环境、修复、重试或配置步骤时才可继续。
- 平台或 ABI 不兼容时，只有剩余计划提供不违反用户约束的兼容容器、隔离环境或已证明兼容的运行时方案才允许继续。
- 校验命令不存在、明确的网络下载失败，以及没有恢复路径的硬阻断属于程序边界，模型不能覆盖。
- 审计日志分别保存“后置校验失败异常复核”和“后置校验最终决策”，便于区分模型建议与程序裁决。

## 18. 终态总结与状态卡片

- 成功、失败、用户终止都必须生成独立的本轮总结；调整计划生成失败也不能只修改任务状态。
- 失败总结优先使用最后失败步骤的模型复核、结构化失败原因和真实输出，并列出失败前已经确认的有效结果。
- 只要关键步骤失败且没有后续证据证明目标达成，总结必须明确说明“任务未完成”，不能用 HTTP 200、进程存在或部分产物掩盖最终内容校验失败。
- `needs_adjustment` 不是最终结束，显示琥珀色“当前阶段结论”；继续调整后可以被新的计划和最终总结替代。
- 成功总结使用绿色、失败总结使用红色、取消总结使用中性灰色、需要调整使用琥珀色；当前计划卡与历史计划卡使用相同状态边框。
