## 业务流中的主要浪费

### 1. 历史事实重新进入完整上下文

最大输入出现在 `model-1788579081730-1`：38,071 input Token。该请求的 `knownExecutionFacts` 单字段为 79,480 个序列化字符，包含 12 个历史步骤。许多步骤同时携带 `output`、`result.facts`、`evidence.facts` 和 `evidence.rawOutput`；路径发现、配置读取和构建入口确认不断重入后续请求。

本轮新增同一步骤内的无损引用：

- 与 `output` 相同的证据原文改为 `rawOutputRef: "output"`。
- 与同一步骤 `result.facts` 完全相同的字段通过 `factsFromResult` 指定共享键；独有或冲突事实原样保留。
- 合法工具 JSON 在模型上下文中按对象提供，避免再次包成带大量转义和缩进的字符串。普通 Shell 文本与不可解析的旧工具结果保留原表示。
- 保留证据 ID、来源、采集时间、scope 和目标上下文。完整本地 ledger 不变；引用只指向本次请求中的字段，不依赖模型记住上一轮。

将实际投影函数离线应用于日志里已有的字段表示：最大 `knownExecutionFacts` 从 79,480 变为 47,521 字符，减少 31,959，约 40.2%；9 个含历史事实的上下文合计从 214,000 变为 143,580 字符，约减少 32.9%。这是已记录字段的投影对照，不含新增说明、证据元数据与其他上下文字段，也不是整个任务的 Token/费用实测下降。

本轮没有扩大或收紧既有历史窗口和文本截取规则。更完整的证据按需检索仍需下一轮实现。

### 2. 已被确定性规则约束的分支仍先问模型

非诊断命令执行失败、剩余计划又没有恢复步骤时，原流程先让模型选择 continue/complete/adjust；continue/complete 最终都会被规则改成 adjust，随后再调用模型生成恢复计划。

现在直接保留失败并进入调整，由下一次规划模型分析错误和生成恢复方案。诊断命令、存在待执行恢复步骤的情况仍保留模型判断。最终验收、用户约束、审批和失败状态没有被绕过。审计将跳过的复核记录为 system，并明确 `modelReviewSkipped`，不伪造模型决策。

日志中有 8 次失败复核没有剩余步骤，相关调用共 13,440 Token；这只是候选路径成本。实际是否可省还必须满足非诊断条件，并受新规划结果影响，不能直接从总成本中扣除。

### 3. 长任务每 30 秒重复请求等待意见

35 次长任务复核均带有活动进程与 CPU/I/O 进展证据，累计 43,624 Token。这些调用并非都能删除：新错误和周期性策略检查仍需要判断。

现在每 30 秒继续运行态采样；仅在 progressive 任务有真实 CPU/I/O 活动、没有未审阅的新错误时，推迟普通模型复核至 120 秒。仅有子进程存在不足以推迟复核。新错误、无可验证进展、采样不可用继续走原复核路径；进程组消失、既有停滞门禁和普通命令 90 秒上限继续生效。模型意见不能代替主命令真实退出和独立后置验收。

完成时新增一条本地调用统计，记录采样轮次、实际模型复核次数和跳过次数，以便新版日志直接比较。

### 4. 失败安装可能已经改变环境

`buildCommandFailure()` 原本写入 `commandCompleted: false`，而状态失效函数把它当成“没有发生变更”。但 `npm install && npm run build` 可能在安装成功之后构建失败，旧依赖或文件观察已经过期。

现在区分命令已分派和成功完成。真实失败或主动中断的变更会使旧观察失效；历史日志可通过真实退出码或 main evidence 判断。未执行的计划、安全拦截和工具解析失败仍不失效旧证据。同一失败命令没有实质调整仍不能盲目重试。

## 工具与 Skill 调整

- `files.read_content` 的说明与已有 `read_batch` 执行契约统一：多个已知且独立的文件可以同轮逐项读取，整批后分析，失败停止剩余步骤；路径依赖上一步结果时另起阶段。这里仍是顺序批处理，没有声称实现远端并行读取。
- 部署 Skill 去掉容易诱导逐文件重新规划的表述，要求复用已有路径，只读取当前决策相关内容，不默认读取完整锁文件或重复扫描整个仓库。
- 构建 Skill 添加首轮发现契约，保留执行可观察性、错误恢复、长任务中断边界与最终验收。首次执行之后恢复完整规则；规则被用户编辑、缺少契约或主动展开时保守回退。
- 安装与构建分别执行、分别验收，避免构建失败使已成功安装被无条件重做。已知步骤不强制拆成多个模型轮次。
- 修正 npm 参数语义：日志最后一次计划声称 `--production=false` 排除开发依赖，据此去掉参数后重装。官方文档明确该参数可用于包含开发依赖；新版 Skill 要求检查 npm 版本、环境与 omit 配置、声明、锁文件和实际安装树，不能据这个错误解释认定缺少 autoprefixer 的原因。[npm install 官方文档](https://docs.npmjs.com/cli/v11/commands/npm-install/)
- 锁文件依赖的安装参数应保持一致；不能无证据添加 force/legacy-peer-deps，也不能把已有项目必要配置一律删除。[npm ci 官方文档](https://docs.npmjs.com/cli/v11/commands/npm-ci/)
- 调整失败的界面日志改为“调整计划生成失败”，避免把供应商额度限制误报为格式异常；底层真实错误信息保留。

## 下一轮优先级

2026-09-06 已落实第 3 项首批阶段契约：通过关联的完整工具证据与 npm/Maven 声明解析推进构建、部署阶段；其他格式保留完整规则展开。具体范围、失效边界与验证见 [阶段证据优化记录](SKILL_EVIDENCE_OPTIMIZATION_2026-09-06.md)。下面的资源版本、范围读取和真实成本评估仍待后续实现。

1. **带资源身份的证据存储与检索工具。** 记录 server、规范化路径、文件版本/mtime/哈希、采集时间与完整性。上下文列出相关证据目录，完整内容按引用读取；模型不能把未检索的引用当作已知正文。当前目标级失效较保守，尚不具备资源级 TTL 或外部修改感知。
2. **文件读取支持行范围与文件列表。** 每文件独立成功/错误/截断信息，返回覆盖范围，避免一份大锁文件挤占后续决策。这里是工具分页能力，不是模型输入/输出 Token 限制。先补范围读取，再考虑经安全审计的并行执行。
3. **以明确产物推动 Skill 阶段。** 例如项目根目录、manifest、包管理器、锁文件一致性、实际 artifact 路径分别形成结构化证据；不能只凭调用过 files.read_content 就认定整个项目已识别。核心编排器处理条件，领域规则留在 Skill；自定义 Skill 保留展开通道。
4. **减少相同路径和安装策略的语义重复。** 现有规范化命令去重只能识别语法身份，不能证明两个不同 find 命令或两种 npm 参数组合在业务上等价。应通过所需证据与已覆盖范围判断，并对变更后的复查保留失效边界。
5. **按成功任务评估。** 用同一组首次部署、已有环境、凭据错误、网络中断、配置修改后复验任务，比较验收成功率、用时、人工介入、模型调用、输入输出 Token、缓存占比与供应商实际账单。缓存优化放在重复业务轮次之后。
