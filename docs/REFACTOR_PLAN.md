## 1. 目标与范围

本轮重构解决两个问题：

1. 将智能需求处理从 `src/stores/ops.ts` 中拆分为边界清晰、可测试的领域模块。
2. 建立统一工具系统，让管理员可以维护模型可见的工具说明，并新增“文件数据结构获取工具”，帮助模型在部署、排障和代码分析前了解远端项目结构。

本轮必须交付：

- 工具注册表和统一工具协议。
- 工具管理界面，支持启用/停用工具并编辑模型可见信息。
- 工具配置持久化、校验、恢复默认值和模型上下文注入。
- 文件数据结构获取工具，支持指定目录、排除目录、深度限制和节点数限制。
- 智能处理核心模块拆分，以及与工具系统的集成测试。
- 清晰的日志、错误提示、代码规范和注释规范。

本轮不包含：

- 允许用户在界面中编写或执行任意工具代码。
- 第三方插件市场和在线工具安装。
- 多服务器并发批量执行。
- 将全部本地数据立即迁移到 SQLite。
- 一次性重写终端、SFTP 或现有任务界面。

## 2. 当前基线与重构边界

现有项目已经具备服务器管理、SSH/SFTP、终端、实时指标、模型配置、任务计划、审批、执行、复查、敏感变量和日志闭环，不应推倒重写。

当前主要问题是 `src/stores/ops.ts` 同时负责状态、上下文、审批、执行、校验、敏感变量和审计。新增工具不能继续以硬编码字符串散落在 store 或提示词中，应先建立唯一工具注册表。

重构后职责如下：

```text
Vue 页面/组件
    -> Pinia（状态与页面协调）
        -> AgentService（智能任务用例）
            -> AgentContext（模型上下文）
            -> ToolRegistry（工具定义与模型说明）
            -> ToolExecutor（工具调用路由）
            -> TaskMachine（状态迁移）
            -> ExecutionRunner（命令执行）
            -> EvidenceReview（证据复查）
        -> backend.ts（前端后端适配）
            -> Tauri commands / 浏览器演示实现
```

约束：

- Pinia 只保存状态并编排服务调用，不承载核心判断算法。
- 模型只能看到已启用工具的脱敏元数据。
- 工具的实现标识、输入契约和安全策略由程序控制，不能在界面中被改成任意代码。
- 远端真实结果优先于模型推断，模型不能将失败改写为成功。
- 不改变现有 Tauri command 名称；新增 command 使用独立名称。

## 4. 统一工具协议

### 4.1 工具定义

新增 `ToolDefinition`，作为工具管理界面、模型上下文和执行路由的唯一数据源：

```ts
export interface ToolDefinition {
  id: string;
  implementation: string;
  name: string;
  description: string;
  usageInstructions: string;
  inputSchema: Record<string, unknown>;
  outputDescription: string;
  enabled: boolean;
  builtIn: boolean;
  version: number;
  updatedAt: string;
}
```

字段规则：

| 字段 | 是否可编辑 | 说明 |
|---|---:|---|
| `id` | 否 | 稳定唯一标识，用于配置覆盖和日志关联 |
| `implementation` | 否 | 程序内部执行器标识，防止界面配置任意代码 |
| `name` | 是 | 展示给用户和模型的工具名称 |
| `description` | 是 | 工具能力、适用场景和边界 |
| `usageInstructions` | 是 | 模型选择工具时必须遵守的调用规则 |
| `inputSchema` | 首版只读 | 程序校验参数的 JSON Schema |
| `outputDescription` | 是 | 返回字段和结果语义 |
| `enabled` | 是 | 是否允许进入模型上下文和被调用 |
| `builtIn` | 否 | 内置工具标记 |
| `version` | 否 | 默认定义版本，用于兼容配置升级 |

首版内置工具：

- `server.basic_info`：服务器基本信息获取。
- `server.realtime_metrics`：服务器实时数据获取。
- `secret.metadata`：服务器敏感信息元数据管理。
- `secret.merge_command`：敏感占位符合并。
- `user.request_input`：根据 schema 请求用户输入。
- `files.get_structure`：远端文件数据结构获取。

### 4.2 默认定义与用户覆盖

- `toolCatalog.ts` 保存只读默认定义。
- `toolRegistry.ts` 将默认定义与用户覆盖合并。
- 持久化时只保存可编辑字段的覆盖值，不复制实现标识和安全契约。
- 默认定义升级时，未被用户修改的字段自动获得新默认值。
- 删除用户覆盖等价于“恢复默认”，不能删除内置工具实现。
- 旧配置解析失败时保留默认工具并记录 warning，不阻断应用启动。

短期使用 `localStorage` 键 `opsark.toolOverrides`。后续迁移 SQLite 时保持 `ToolRegistryRepository` 接口不变。

### 4.3 模型上下文

`buildToolContext()` 只序列化已启用工具，并包含：

- `id`、`name`、`description`。
- `usageInstructions`。
- `inputSchema`。
- `outputDescription`。

禁止进入模型上下文：

- 工具执行函数或内部 command 名称。
- SSH 密码、API Key、敏感变量 value。
- 已停用工具。
- 仅供 UI 使用的编辑状态。

模型请求日志保存脱敏后的工具快照和版本，便于追溯模型为什么选择某个工具。

### 4.4 调用与校验

模型工具调用统一为：

```ts
export interface ToolCall {
  id: string;
  toolId: string;
  arguments: Record<string, unknown>;
}

export interface ToolResult<T = unknown> {
  callId: string;
  toolId: string;
  success: boolean;
  data?: T;
  error?: { code: string; message: string };
  truncated?: boolean;
}
```

执行前必须依次检查：工具存在、工具已启用、参数符合 schema、当前服务器可用、调用符合权限策略。所有调用产生审计日志，但日志不得包含敏感值。

## 5. 工具管理界面

在设置页增加“工具管理”区域，使用独立组件，避免继续扩大 `SettingsView.vue`。

### 5.1 页面能力

- 按名称、ID 和说明搜索工具。
- 查看工具状态、类型和最近修改时间。
- 启用或停用工具。
- 编辑名称、说明、使用规则和输出说明。
- 只读查看输入 schema。
- 保存单个工具或保存全部修改。
- 恢复单个工具默认值。
- 显示未保存、保存中、成功和失败状态。

交互要求：

- 停用工具前说明它将从后续模型上下文中移除。
- 必填字段为空、内容仅为空白或超出长度时禁止保存并就地提示。
- 修改工具说明不会改变底层执行权限。
- 内置工具不能删除；首版不提供“新增自定义执行器”按钮。
- 窄屏下编辑区改为单列，字段和按钮不得重叠。

### 5.2 表单校验

- `name`：1 到 80 个字符。
- `description`：1 到 1000 个字符。
- `usageInstructions`：1 到 2000 个字符。
- `outputDescription`：1 到 1000 个字符。
- 所有文本保存前 `trim()`。
- 保存后重新从注册表读取，确保 UI 展示的是实际生效值。

### 5.3 验收

- 修改工具说明并保存，刷新页面后仍存在。
- 新建模型请求时日志中的工具快照包含新说明。
- 停用工具后，它不再出现在模型上下文中，执行器也拒绝其调用。
- 恢复默认后，界面和模型上下文都使用默认定义。

## 6. 文件数据结构获取工具

### 6.1 用途与边界

`files.get_structure` 用于读取远端服务器上指定目录的文件和目录结构，典型场景包括项目部署前识别技术栈、定位入口文件、了解配置分布和辅助生成后续只读发现计划。

该工具只返回结构和基础元数据，不读取文件内容，不跟随符号链接，不修改远端文件。

### 6.2 输入参数

```ts
export interface FileStructureRequest {
  rootPath: string;
  excludeDirectories?: string[];
  maxDepth?: number;
  maxNodes?: number;
  includeHidden?: boolean;
}
```

参数规则：

- `rootPath`：必填，必须是远端绝对目录路径。
- `excludeDirectories`：目录名或相对 `rootPath` 的路径；禁止使用绝对排除路径和 `..`。
- `maxDepth`：默认 6，范围 1 到 20。
- `maxNodes`：默认 2000，范围 1 到 10000。
- `includeHidden`：默认 `false`。

默认排除目录：

```text
.git, node_modules, vendor, dist, build, target, coverage,
.cache, .next, .nuxt, .venv, venv, __pycache__, logs
```

用户传入的排除项与默认排除项合并。后续若需要扫描某个默认排除目录，应新增显式 `useDefaultExcludes` 参数，不通过特殊字符串绕过。

### 6.3 返回结构

```ts
export interface FileStructureNode {
  name: string;
  relativePath: string;
  kind: "file" | "directory" | "symlink" | "other";
  size?: number;
  children?: FileStructureNode[];
}

export interface FileStructureResult {
  rootPath: string;
  nodes: FileStructureNode[];
  excludedDirectories: string[];
  totalNodes: number;
  maxDepthReached: boolean;
  truncated: boolean;
  warnings: string[];
}
```

返回要求：

- 每层先目录后文件，并按名称稳定排序。
- `relativePath` 使用 `/`，不返回服务器密码等连接信息。
- 无权限目录写入 `warnings`，其他可访问部分仍正常返回。
- 达到深度或节点限制时返回已取得的结构，并明确标记 `truncated`。
- 根目录不存在、不是目录或 SSH 失败时返回结构化错误，不伪造空树。

### 6.4 后端实现

在 Rust 新增 `file_tree.rs` 和 Tauri command `get_remote_file_structure`：

1. 复用现有 SSH 连接参数和认证流程。
2. 使用 SFTP API 遍历，不拼接执行 `find` 命令，避免 shell 注入和不同系统命令差异。
3. 规范化并验证 `rootPath`、排除项、深度和节点数。
4. 使用显式栈或受限递归遍历，节点计数达到上限后立即停止。
5. 不跟随符号链接；只记录链接节点。
6. 将可恢复的目录读取错误转成 warning，将根路径错误转成 command error。
7. 在 `lib.rs` 注册 command，前端只通过 `backend.ts` 调用。

浏览器演示模式返回固定但符合真实契约的项目树，并覆盖排除、深度和截断行为，便于无 SSH 环境开发 UI 和测试。

### 6.5 模型使用规则

给模型的默认说明必须明确：

- 部署或修改未知项目之前，先获取项目结构，再根据真实文件决定下一步。
- 不得根据目录名猜测文件内容。
- 结构信息不足时，再计划读取少量关键文件，不得无边界读取整个项目。
- `truncated=true` 时，应缩小目录或调整排除项继续获取，不能声称已扫描完整项目。
- 工具是只读发现工具，调用风险为低。

### 6.6 测试与验收

Rust 单元测试：

- 默认排除目录生效。
- 自定义目录名和相对路径排除生效。
- `..` 和绝对排除路径被拒绝。
- 隐藏文件开关生效。
- 深度和节点上限生效且正确标记截断。
- 符号链接不被跟随。
- 无权限子目录生成 warning，不丢失其他节点。
- 输出排序稳定。

前端测试：

- 请求参数规范化正确。
- Tauri DTO 到 TypeScript 类型映射正确。
- 工具停用时无法调用。
- 工具结果可进入当前任务的脱敏上下文和审计日志。

手动验收示例：

```text
rootPath: /opt/my-app
excludeDirectories: ["uploads", "storage/cache"]
maxDepth: 5
maxNodes: 1500
includeHidden: false
```

验收结果应包含 `/opt/my-app` 下允许访问的完整结构，不包含 `uploads`、`storage/cache`、默认排除目录及其后代。

## 7. 智能处理模块职责

### `agentContext.ts`

- 组合固定系统提示词、服务器信息、实时指标、历史任务、终端引用、已启用工具和敏感变量元数据。
- 统一裁剪上下文并生成脱敏审计摘要。
- 不读取工具配置存储，只接收 `ToolRegistry` 的解析结果。

### `taskMachine.ts`

- 集中定义合法状态迁移。
- 每次迁移返回新状态和审计事件。
- UI 不直接修改复杂任务状态。

```text
draft -> planning -> awaiting_plan_approval -> running
running -> awaiting_step_approval | awaiting_input | validating
validating -> running | needs_adjustment | completed | failed
任意可终止状态 -> cancelled
```

### `stepMachine.ts`

- 集中定义步骤从待执行、审批、敏感输入、运行和校验到终态的合法迁移。
- 已完成、失败和跳过均为终态，禁止重新进入执行队列。
- store 不再直接写入生产步骤的 `status` 字段。

### `toolStepResult.ts`

- 将工具成功、截断和失败结果转换为统一的步骤结果、证据和规则复核。
- 生成稳定的进度文案、任务事件和失败暂停原因。
- 不访问 Pinia、后端或模型，可独立测试。

### `toolStepLifecycle.ts`

- 统一工具步骤启动时间、运行状态、耗时和结构化结果写回。
- 将执行边界抛出的异常转换为稳定工具失败结果。
- 异步工具返回后先检查取消状态，禁止覆盖用户终止结果。
- 返回任务状态、事件消息和是否继续推进，由 store 提交副作用。

### `commandStepResult.ts`

- 统一构建长任务复查中止和主命令失败时的结果与执行证据。
- 将校验分类结果和标准校验器一次性写回步骤。
- 保证 `StepResult.evidenceIds` 与实际证据 ID 一致。
- 主命令失败通过状态机一次性写回状态、结果和证据。

### `reviewService.ts`

- 独立协调前置条件、主命令失败和执行证据三类异常复查。
- 同时保留模型原始决策与确定性规则修正后的最终决策。
- 通过参数注入模型复查函数，不依赖 Pinia。

### `executionDispatch.ts`

- 在执行前纯函数判断工具调用、敏感输入等待、远程命令或协议错误。
- 工具协议校验优先于 shell 敏感占位符识别。
- 只返回分派决策，不修改任务和步骤。

### `stepExecutionEntry.ts`

- 消费执行分派结果并统一写入协议失败、敏感输入等待或命令启动状态。
- 返回稳定任务目标状态、暂停原因、事件消息和终端标题。
- 未预期异常统一复用中断模块生成失败结果。

### `stepInterruption.ts`

- 统一取消、协议解析失败、执行异常和敏感输入等待/恢复的步骤写回。
- 取消和异常终态始终生成结构化 `StepResult`。
- 保留中断前已收集证据的引用关系。

### `executionLifecycle.ts`

- 统一远程命令、长任务监控和独立校验的启动与清理顺序。
- 命令和每次校验均通过 `finally` 清理当前执行 ID。
- 对只读 HTTP 校验执行一次有界重试，并返回首次失败输出供 UI 留痕。
- 通过依赖注入执行器和监控器，可独立覆盖异常与取消竞态。

### `executionPreparation.ts`

- 规范化命令和校验中的敏感占位符。
- 分离占位符模板与仅供执行器使用的解析后值。
- 统一准备SSH连接和可选模型运行参数。
- 不记录、不持久化解析后的敏感值。

### `executionAudit.ts`

- 统一主命令结果和程序证据校验的审计结构。
- 命令日志只使用占位符模板及已脱敏输出。
- 根据校验是否接受及观察状态确定成功、警告或错误等级。

### `validationOutput.ts`

- 统一首次校验失败与最终校验输出的步骤文本分隔格式。
- 将缺失的校验输出规范化为空字符串，不把 `undefined` 写入持久化结果。
- 主命令无输出时直接从校验标题开始，避免无意义的前导空行。

### `terminalBuffer.ts`

- 统一百分比进度帧替换、命令完成输出和校验输出追加。
- 所有写入共享终端行数上限，避免不同执行入口无限增长。
- 流式命令只追加最终退出行，避免重复显示完整输出。

### `reviewCoordination.ts`

- 将前置条件、长任务调整、失败复查和证据复查的最终决策转换为状态、消息和是否继续推进。
- 前置条件复查统一写回最终结论，并明确当前步骤是否允许执行。
- 长任务调整统一写回步骤复查结论、失败结果和执行证据。
- `complete` 决策统一跳过无需继续的剩余步骤。
- `adjust` 决策统一生成暂停原因并停止推进。

### `reviewAudit.ts`

- 将复查上下文、模型决策和规则最终决策投影为稳定审计结构。
- 执行证据复查按模型、最终规则、阻断门禁顺序生成事件。
- store 只提交审计草稿，不再手工维护日志 JSON 字段。

### `stepReviewPipeline.ts`

- 组合前置条件、命令失败和执行证据三类复查的服务、审计投影和状态协调。
- 在异步复查完成后优先检查取消状态，再应用领域结果。
- 返回有序审计和协调结果，由store统一持久化和继续推进。

### `stepApproval.ts`

- 复用审批策略判断步骤是否需要单独确认。
- 通过步骤状态机进入等待审批状态，并生成统一风险提示。
- 仅允许处于等待审批状态的步骤恢复执行，实际执行仍由 store 调度。

### `taskAdvancement.ts`

- 组合发现续规划的模型可用性、生成结果、自动审批判定和取消检查。
- 组合完成总结与模型请求、模型返回和任务完成审计。
- 不修改任务对象，由 store 根据结构化结果提交状态、计划和消息。

### `taskProgression.ts`

- 从任务消息中取得最新用户需求，忽略操作事件。
- 统一返回“执行下一步”、“根据发现证据续规划”或“进入完成总结”。
- 过滤已执行和同批次重复的续规划命令。
- 在变更步骤前识别最新未解决阻断证据，仅有中间成功的修复变更可以清除阻断。

该模块只返回推进决策，不修改任务状态，不调用模型或后端。

### `approvalPolicy.ts`

- `observe`：所有步骤确认。
- `safe`：低风险自动，中高风险确认。
- `managed`：计划自动批准，低中风险自动，高风险确认。
- 高危破坏性操作始终需要步骤级确认。
- 历史 `autonomous` 配置加载时迁移为 `safe`。

### `executionRunner.ts`

- 接收执行期已合并敏感占位符的命令，并调用后端执行器。
- 通过脱敏进度回调向终端和任务时间线输出。
- 命令与独立校验使用相同的输出清洗和脱敏边界。
- 所有日志和 UI 输出使用脱敏版本。

### `longRunningMonitor.ts`

- 独立管理命令心跳、长任务提示和 30 秒定期复核。
- 防止定期复核重入，并在命令结束时统一回收定时器。
- 只有模型真实决策可以停止持续等待；`complete` 还必须有独立校验通过的证据。
- 停止决策和异常通过回调写回 store，监控器不直接依赖 Pinia。

### `evidenceReview.ts`

- 分类执行结果和观察结果。
- 执行独立 validation 并生成证据。
- 确定性事实优先于模型判断。
- 只围绕失败步骤和未完成目标调整计划，不重复已完成步骤。

### `secretTool.ts`

- 只向模型暴露 key、description、scope 和 placeholder。
- 真实 value 保存到系统钥匙串并仅在执行期注入。
- 用户输入先暂存，步骤复查成功后再提交保存。

### `auditTrail.ts`

- 统一记录任务、模型、工具、命令、SSH、SFTP 和敏感变量变更事件。
- 工具事件至少包含 `toolId`、调用参数摘要、结果摘要、耗时和截断状态。
- 任何日志不得包含敏感值或合并后的真实命令。

## 9. 代码与注释规范

### TypeScript/Vue

- 开启并遵守现有 TypeScript 严格检查，不使用无理由的 `any`、非空断言或类型强转。
- 领域类型集中在对应 feature 的 `types.ts`，跨层 DTO 显式转换。
- 组件保持单一职责；列表、编辑器和页面容器分别实现。
- 业务判断写成纯函数，异步副作用集中在 service 或 store action。
- 用户输入、localStorage 数据和后端返回都必须经过运行时校验或规范化。
- 错误使用稳定 code 和用户可读 message，不依赖字符串匹配驱动业务逻辑。

### Rust

- command 只负责参数接收、调用领域函数和返回 DTO。
- 路径、排除项、深度和数量在进入遍历器前完成校验。
- 不使用 `unwrap()` 处理网络、SFTP、路径或用户输入。
- 可恢复子目录错误进入 warnings；不可恢复错误返回 `Result::Err`。
- DTO 使用统一 `camelCase` 序列化并与 TypeScript 类型逐字段对应。

### 注释

- 注释解释“为什么有此约束”或“不明显的安全边界”，不复述代码。
- 公开领域函数写简短文档注释，说明输入、返回值和关键错误条件。
- 文件遍历的符号链接策略、节点限制、排除匹配规则必须有注释。
- 敏感信息脱敏和工具执行权限边界必须有注释。
- 临时兼容逻辑使用 `TODO` 时必须写明移除条件，禁止无上下文 TODO。

示例：

```ts
// Only editable fields are persisted so catalog security updates cannot be shadowed
// by stale local copies of implementation metadata.
```

```rust
// Symlinks are reported but never traversed to keep the scan inside the requested tree
// and prevent cycles.
```

### 提交约束

- 一个阶段一个独立变更集，不混入无关格式化或视觉重构。
- 新增行为必须有对应测试；修复缺陷时先增加可复现测试。
- 修改公共契约时同步更新 TypeScript、Rust、演示适配器和文档。
