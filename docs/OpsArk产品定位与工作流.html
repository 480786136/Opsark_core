把运维从「查命令、试命令」

OpsArk 是运行在桌面的智能运维执行体。它直连你的服务器，感知真实环境，把一句自然语言需求拆成带风险等级的执行计划， 在隔离终端里逐步执行、独立校验、自动调整，最终交出可审计的完整证据链 —— 而不是给你一段需要自己复制粘贴的命令。

全链路闭环 需求 → 计划 → 审批 → 执行 → 校验 → 总结
真执行 独立 Agent 沙箱终端 · 真实退出码

凭据不出本机 系统钥匙串 · 全链路脱敏

01

产品定位

先把边界说清楚。OpsArk 的价值不在"AI 很聪明",而在"它真的能把事情做完、做对、说得清"。

它是

  • 会连服务器、会执行、会自检的运维执行体规划与执行在同一条链路上闭合，不是建议器
  • 带风险分级与人工确认的变更管控工具三档授权 + 高危命令强制人工逐步确认
  • 把团队 SOP 沉淀成 Skill 的流程资产部署、数据库、文件传输等领域工作流可复用可同步
  • 可回溯的审计与交接凭据每一步的命令、输出、校验结论完整留痕

它不是

  • 不是聊天问答 / 命令生成器不输出让你自己复制粘贴的答案
  • 不是监控告警看板不做 Agent/指标平台那套采集告警生态
  • 不是 Ansible / Jenkins 的替代品不编排既定流水线，处理的是临时、模糊、需要判断的活
  • 不是云端 SaaS 控制台本地优先，服务器与凭据留在你的机器上
POSITIONING LINE
一句话运维：说清楚要什么，剩下的它做完、验完、记完。
02

工作流

上层是用户感受到的五步，下层是系统真正跑完的十步闭环。宣传用上层，技术可信度靠下层。

用户视角 · 五步
STEP 01
纳管服务器
填一次连接信息，自动探测并采集物理信息与软件环境
STEP 02
说一句话
"检查这台机器为什么慢""把项目部署起来"
STEP 03
看计划
每一步要跑什么命令、为什么、风险多高，全部展开可查
STEP 04
点确认
低风险自动跑，中高风险弹给你确认，危险操作永远人工
STEP 05
拿结果
实时回显 + 独立校验 + 完成总结 + 完整审计记录
系统视角 · 十步闭环
感知 环境快照
  1. 连接与探测SSH 直连、连通性测试、凭据恢复
  2. 环境与指标采集CPU/内存/磁盘/网络 + 已部署软件清单
理解与规划 生成计划
  1. 需求分类意图、目标关系、变更边界（只读/指定变更）
  2. Skill 选择与编排命中领域工作流，可多 Skill 组合
  3. 分阶段计划生成每步含命令、预期、校验、风险等级
执行与校验 逐步推进
  1. 分级审批三档授权 + 高危强制人工 + 计划快照失效校验
  2. 沙箱执行独立 Agent 会话，不污染用户终端，取真实退出码
  3. 独立后置校验只读、独立、能证伪预期；有界稳定窗口重试
收口 验收与留痕
  1. 异常复核与调整失败事实不可改写，防循环，可续接原目标
  2. 整体目标门禁计划跑完 ≠ 目标完成；部署要验端口/HTTP/日志
  3. 审计归档命令、输出、模型输入输出全程留痕
贯穿全程的三条护栏

安全护栏

风险只能被抬升不能被降低；rm -rf、DROP TABLE、重启等破坏性操作无论授权档位一律人工确认。

命令在下发前至少经过两轮安全检查，第二轮不通过就不发给服务器。

凭据护栏

模型只看到 ${secret.KEY} 占位符，真实口令在执行边界才注入；SSH 密码、Git 令牌、数据库密码按用途隔离，绝不串用。

真实值存系统钥匙串，不写入 localStorage、日志或任何模型上下文。

证据护栏

"命令执行成功"与"观察结果健康"分开判定；校验拿不到真实结束标记就判未完成，不允许模型把失败解释成成功。

失败事实不可改写：非零退出、认证失败、协议不完整都是硬事实。

针对的人群

按"痛感强度 × 付费意愿"排序。前两类是首发主战场，第三类是规模化收入来源。

10–200 人团队 · 无专职运维
会写代码但记不住运维命令，部署/排查靠搜博客。要的是"别让我查了，直接搞定"。
P0 首选

中小团队 IT / 系统管理员

几十到上百台机器

多客户 · 多环境

04

解决的问题

每一条都对应现有实现里的具体机制，宣传时可以逐条拆成场景短视频或落地页模块。

今天运维的真实痛点OpsArk 的解法
01指令记不住，每次都要搜、要试、要翻历史记录自然语言直达执行。模型拿到的是这台机器的真实环境，不是通用答案。
02不确定命令安不安全、会不会误伤生产先出计划再执行，风险分级可见；三档授权控制自动执行范围，高危一律人工确认。
03复制粘贴来回试错，一步报错就要重来执行后自动做独立只读校验，不达标就自动复核、调整计划，失败事实不会被粉饰。
04"以为做完了",其实服务没起来、文件没传全整体目标完成门禁：部署必须验端口、HTTP、日志；传文件必须核字节数与 SHA-256。
05操作前不知道机器现在什么状态进入即采集并持续刷新 CPU / 内存 / 磁盘 / 网络与已装软件环境，规划基于真实快照。
06数据库密码、Git 令牌写在命令里、贴在聊天框里敏感变量库 + 凭据组 + 用途校验，模型只见占位符，真实值只在本机钥匙串与执行边界出现。
07做完说不清做了什么，出事无法回溯，交接断层命令、输出、模型输入输出、审批记录全链路审计，一键导出与工单关联。
08巡检排查靠人肉，覆盖面取决于个人经验全方面检查分析：按领域 Skill 分阶段做发现式检查，不遗漏、有证据、有结论。
09团队 SOP 只存在于老员工的脑子里个人 Skill 可编写、可同步，把"我们公司怎么部署"固化成可复用工作流。
05

宣传亮点

对外传播的五个核心卖点，建议按此顺序做落地页主视觉区。

执

真执行

不是给你命令，是它自己连上去跑。独立 Agent 沙箱终端执行，取真实退出码，你的终端不会被抢占。

验

真校验

每步执行完都跑一次独立的只读后置校验。"命令跑通"不等于"结果正确"，这是与其他工具最大的分水岭。

控

看得见的风险

计划、命令、风险等级全部展开可查；低风险自动跑，中风险问你，高风险永远等你点头。

密

凭据不出本机

口令存系统钥匙串，模型永远只看到占位符；SSH / Git / 数据库凭据按用途隔离，不会串用。

痕

全过程留痕

每一步的命令、输出、校验与审批都有记录，可回溯、可追责、可交接、可作为交付凭证。

Slogan 候选

强调范式转移
会执行、会验证、会留痕的运维搭档。

06

建议主推的三个场景

场景收敛才能做出可传播的 Demo。这三个最能体现"全链路"三个字，也最容易拍成对比视频。

SCENE A

日常巡检 / 健康检查

一句话发起一次全方面检查，输出结构化健康报告。

  • 采集指标与软件环境
  • 按领域 Skill 分阶段发现
  • 每项结论附真实证据
  • 异常项给出建议与风险
SCENE B

故障排查 / 诊断

"服务为什么起不来""机器为什么慢"，从现象一路查到根因。

  • 先只读诊断，不夹带变更
  • 证据不足就请求更多上下文
  • 失败事实不被改写
  • 给出结论 + 修复方案待你确认
SCENE C

部署上线 / 环境搭建

从源码获取到端到端验收，一条需求走完整个交付。

  • 探目录 → 读说明 → 查依赖
  • 装环境 → 构建 → 启动托管
  • 端口 / HTTP / 日志端到端验收
  • 中途可继续、可补充、可替换目标
07

落地前要对齐的几点

作为设计侧的建议：宣传口径需要和能力现状严格对齐，否则第一个 demo 就会翻车。

对外承诺的红线

  1. 别把"AI 聪明"当卖点。市场上给命令的 AI 工具太多了。所有物料的主语应该是"做完、验完、记完"，而不是"懂运维"。
  2. 安全是最大卖点，也是最大顾虑。桌面端直连生产服务器，落地页必须前置回答三件事：凭据在哪、谁能批准、做错了怎么回溯。
  3. 演示要选"有失败"的场景。只演示顺利执行反而削弱可信度。展示一次"校验没过 → 自动调整 → 二次验证通过"，说服力最强。
  4. 暂不宣传未完成能力。大文件传输分片、断点恢复、SQLite 持久化等仍在路上，物料中不要出现相关承诺。
  5. 目标人群先打 P0 两类。兼运维的开发 + 中小团队 IT，他们的痛感最强、决策链最短，落地页文案应该直接用他们的话术。
