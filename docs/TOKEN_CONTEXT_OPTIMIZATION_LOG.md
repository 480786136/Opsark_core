# Agent 上下文与 Token 优化记录

> 创建日期：2026-09-02  
> 记录规则：每次优化单独编号，同时记录“用户真实需求”和“代码真正落地的方案”。后续修改只追加新记录，不用新设计覆盖旧记录。

## 第 1 次：单步骤复核与整体目标复核减量

### 用户需求

- 优化单步骤复核和整体目标复核。
- 不再在复核时反复发送完整终端输出、完整计划和重复的用户需求。
- 保留足够的失败证据，不能因减量造成误判。

### 真正修改的方案

1. 新增 `src/features/agent/reviewPayload.ts`，统一处理复核字段的长度、结构化结果、证据数量、输出指纹和关键异常行。
2. 单步骤复核不再在 JSON 内重复携带外层已传入的用户目标，不再同时发送 `fullPlan`、`remainingSteps` 和重复的步骤全量。
3. 单步骤历史最多发送最近 6 步，待执行步骤最多发送前 6 步，并额外发送计划状态计数，让模型知道有多少内容被省略。
4. 成功历史步骤不再携带大段原始输出；失败、证据冲突和后置校验失败保留有界的头尾内容、关键错误行、长度和指纹。
5. 整体目标复核不再发送无界的当前轮完整 ledger，Skill 验收说明也有独立长度上限。
6. Rust 端复核 system prompt 删除与 JSON 上下文重复的大段规则，保留决策硬边界和严格 JSON 结构。

### 实际边界

- 单步骤失败的当前命令、结果、输出窗口和证据仍会发给模型。
- 本地任务审计记录仍保留原始步骤；“模型上下文减量”不等于“删除本地执行记录”。

## 第 2 次：整体复核和调整计划共用基础上下文

### 用户需求

- 整体目标复核和调整计划使用同一套基础上下文。
- 最近历史希望按“最近两个执行阶段”组织，而不是把步骤从不同轮次中随意截取。
- 更旧的计划步骤和总结应当压缩成一条可持续更新的历史记录，避免调整次数越多、每次输入越大。
- “已验证事实”只能来自真实 `result/evidence`，不能把计划描述或模型阶段总结当作成功证据。
- 在共用上下文之外继续完善 Token 上限、输出截断、Skill/Tool 说明减量和省略历史可追溯性。

### 真正修改的方案

1. 新增 `src/features/agent/taskDecisionSnapshot.ts`，定义整体复核和普通调整计划共用的 `baseSnapshot`。
2. 整体复核只生成一次 `baseSnapshot`。当结论是 `adjust` 时，快照和复核结论写入任务的 `latestGoalReview`；下一次调整计划直接复用，不再从全部历史重新拼一套。
3. `baseSnapshot` 仅保留：
   - 任务状态、权限和执行约束。
   - 结构化进度计数。
   - 当前失败或阻断事件的有界详情。
   - 当前计划的有界步骤。
   - 当前需求轮内最近 2 个已归档执行阶段。
   - 更旧历史的滚动检查点。
   - 被压缩历史的轮次数、阶段数、步骤数和指纹。
4. 当前计划超过 20 步时，优先保留前 3 步、异常步骤（最多 8 步）、即将执行的步骤（最多 6 步）和最近步骤，总数不超过 20。当前事件单独展开，不在步骤列表里重复。
5. 每个最近执行阶段最多发送 12 个步骤。成功步骤只发送结构化结果、证据事实、输出长度和指纹，不发送原始输出；异常步骤才发送有界输出和关键错误行。
6. 新增 `src/features/agent/taskHistoryCheckpoint.ts`，将离开“最近 2 个阶段”窗口的旧阶段增量合并到任务内的结构化检查点：
   - 最多 12 条有 `result/evidence` 支持的已验证事实。
   - 最多 8 条异常/未解决问题及同命令尝试次数。
   - 最多 4 条旧阶段状态摘要。阶段的自然语言总结仅作导航，不变成已验证事实。
   - 累计轮次、阶段、步骤和状态计数，以及对已压缩来源的指纹。
7. 滚动检查点采用本地确定性结构化合并，而不是每次再调一次大模型生成“摘要的摘要”。它达到递归二次压缩的体积效果，同时不新增摘要 Token，不会因多次自然语言转述累积事实漂移。
8. 调整计划仅在共用快照之外增加 `adjustmentTrigger`、当前有界的 Tool 目录和已激活 Skill 说明：Tool 的名称、描述、用法和输出说明分别限长，Skill 说明最多 2,200 字符。
9. 调整原因和整体复核的 `decision/reason/summary` 都有独立长度上限，不再夹带整份复核对话。
10. 安全门禁拒绝是特例：它只发送命中字段、结构化规则和相邻步骤标题，不附加通用快照，避免把不相关命令和原始输出发给局部修复请求。
11. 快照中的命令会脱敏常见的 token/password/API key 命令行参数、URL 查询参数和 URL userinfo；省略的命令保留指纹供重复尝试判断。

### 共用后两次模型调用的实际区别

| 内容 | 整体目标复核 | 普通调整计划 |
|---|---|---|
| `baseSnapshot` | 生成并发送 | 原样复用 |
| 整体目标 | 作为调用外层 requirement 发送 | 作为调用外层 requirement 发送 |
| Skill | 只发送有界的最终验收说明 | 发送有界的已激活 Skill 计划说明 |
| Tool | 不发送 | 发送有界的已启用 Tool 目录 |
| 复核结论 | 由模型返回 | 只追加有界的 `decision/reason/summary` |
| 调整触发原因 | 不需要 | 追加有界的当前阻断说明 |

### 不发给模型但仍保留的内容

- 完整 `planHistory`、`phaseHistory` 和原始步骤仍留在本地任务审计 ledger，供开发者日志、界面展开和确定性重复命令判断使用。
- 已被检查点吸收的旧输出不再进入整体复核和调整计划的模型请求。
- 保留“被压缩数量 + 指纹”，用于判断历史是真的被省略，而不是记录丢失。

## 第 3 次：修复 EACCES 等子串误匹配导致的错误诊断和额外调用

### 用户需求

- 修复 `EACCES` 误匹配导致的错误诊断和大量额外模型调用。
- 同时排查和修复类似的“日志或资源名中包含某个子串，就被当成真实错误”问题。

### 真正修改的方案

1. 确认真实根因为 Maven 依赖名 `com.google.guava:failureaccess`：`failureaccess` 中的跨单词子串被旧规则 `/EACCES/i` 命中，因此实际的 `NoSuchFieldError`/JDK 兼容性失败被写成 `permission_denied`。
2. `analyzeSkillCommandFailure()` 不再用一组正则扫描整段输出并仅返回分类名，而是：
   - 将输出按行处理，超长日志仅扫描前 200 行和后 2,200 行。
   - 只在 `EACCES/EPERM` 作为独立错误码并出现在 npm errno/code、`Error: EACCES: permission denied`、Python `Errno 13` 或 `AccessDeniedException` 等错误形态中时判定权限错误。
   - 每个确定性分类携带最多 360 字符的真实命中行和 `high/fallback` 置信级别，让后续复核不再只看一个无证据的 category。
3. 新增确定性 JDK 兼容性分类：
   - `NoSuchFieldError` / `NoSuchMethodError` / `IllegalAccessError` 指向 `com.sun.tools.javac` 或 `jdk.compiler` 时，分类为 `jdk_tooling_incompatible`。
   - `UnsupportedClassVersionError`、`class file has wrong version`、`invalid target release` 等分类为 `jdk_version_incompatible`。
4. 同样收紧 `ENOSPC`、command-not-found、网络错误码和 HTTP 404 的匹配，并保留真实证据行；无高置信信号时回退为 `command_failed`，不猜测具体原因。
5. 长任务关键行中的 `error/failure/failed` 改为单词边界匹配，`failureaccess` 不再被当成 critical failure；同时显式保留 `NoSuchFieldError`、`TypeError`、`AccessDeniedException` 等命名异常。
6. SFTP 目录错误码中的 `eacces/enoent` 增加单词边界，不再把文件名或依赖名当成错误码。
7. 调整 incident 不再通过失败步骤的业务原始输出猜测 transport 故障。只有执行器已写入 `terminal_transport/terminal_recovery/validation_protocol_exception`、终端实际 busy，或无失败步骤时的编排层错误才进入 transport 恢复。远程应用日志中的 `connection closed` 仍是 business failure。

### 调用数影响

- 真实命令失败仍会进行一次必要的失败复核，不会为了减少 Token 而把失败当成成功。
- 修复的是“错误 category 成为模型硬事实后，连续生成权限、SELinux、挂载、重试等无关计划”的级联。新分类会直接提供真实 JDK 错误行，让第一次复核和下一次调整面向真实原因。

### 验证记录

- 增加 `failureaccess` 真实 Maven 路径、真实 npm `EACCES`、普通文本 `EACCES`、JDK `NoSuchFieldError`、command-not-found、DNS 失败、HTTP 404、`ENOSPC`、长任务关键行、SFTP 错误码和 business/transport 分类回归。
- 前端全量 Vitest：80 个测试文件，515 项通过，16 项既有用例按设计跳过。
- TypeScript 检查、Vite 生产构建和 `git diff --check` 通过。

## 第 4 次：协议重试、工具上下文与阶段末双调用优化

### 用户需求

- 根据完整开发者调用日志修复 Token 消耗过大的问题。
- 不通过限制输入 Token、输出 Token、计划步骤或字段长度来换取成本下降。
- 优化必须保持通用编排能力，同时保留 Skill 的领域针对性和最终验收质量。

### 真正修改的方案

1. 修复计划协议的类型矛盾：提示词统一要求工具步骤输出 `"validation":"true"`；Rust 只在模型响应 DTO 边界兼容布尔 `true` 并立即规范化为字符串，继续拒绝 `false`、`null`、数字、数组和对象。普通 Shell 步骤仍会拒绝无意义的 `true` 校验。
2. `opsark-tool` 改为严格的单行原子调用：一条命令只能有一个工具 ID 和一个参数对象。standalone 工具与其他 pending 步骤共存时整份计划关闭式拒绝，不再静默删除依赖步骤。
3. 给工具增加受信任的 `modelExposure`：`server.basic_info`、`server.realtime_metrics` 只作为程序采集的上下文；`secret.metadata`、`secret.merge_command` 只在内部执行边界使用。这 4 个当前不可由模型外部调用的定义不再进入规划请求，通用目录从 11 个降为最多 7 个。
4. 内置 Skill 增加保守的整个工作流工具允许集，选中单个内置 Skill 时通常只发送 1～4 个工具完整 Schema；多 Skill 取允许并集和禁止并集。无 Skill、旧版 Skill 或自定义 Skill 没有允许集时，保留完整 planner 目录，避免为省 Token 隐藏未知业务能力。
5. 工具允许集不仅用于裁剪提示：Rust 模型响应校验和前端执行分派都会拒绝当前规划上下文未暴露的工具；旧版上下文缺少 `tools` 字段时保留兼容行为。
6. 新增 `decide_ai_next_stage` 联合协议，把阶段结束后的整体完成判断与“未完成时的下一阶段计划”合并为一次模型调用。`complete` 必须携带空 `steps`，`continue/adjust` 必须携带至少一个通过现有安全、Skill 与工具策略校验的步骤。
7. 联合响应中的后续计划随整体判断一起保存，使用执行事件指纹和策略指纹校验新鲜度；策略变化覆盖目标轮次、权限、模型、执行约束、Skill 指令与工具策略、工具完整说明和凭据元数据。命中缓存后直接进入原审批/执行链，不再发送同一快照生成第二份计划。
8. 修复 Pinia 响应式计划不能直接 `structuredClone` 的 `DataCloneError`。缓存计划先按持久化 JSON 契约转为普通对象，防止本地复用失败后意外退回第二次模型调用。
9. 调整、发现续接和联合决策上下文将相对稳定的工具、Skill 与规则字段放在动态证据之前，为供应商前缀缓存提供更稳定的布局；没有删除结构化结果、失败证据、用户约束或完整 active Skill 指令。

### 调用与上下文影响

- 正常“阶段结束但整体目标未完成”路径由“整体复核 + 调整计划”两次模型调用变为一次；按分析日志中的 14 组连续路径，理论上可直接消除约 14 次重复调用。异常或新旧桌面端版本不一致时仍会失败关闭并回退旧复核路径，避免错误完成。
- 通用规划请求不再发送 4 个不可外部调用工具；内置 Skill 任务通常只发送其 1～4 个可能工具。旧版/自定义 Skill 使用保守回退，因此不会因缺少新元数据降低可完成性。
- 本轮没有新增模型调用次数预算、输入 Token 上限、输出 Token 上限或自动截断。真实节省量仍需使用同一任务回放或下一份生产日志复测，不能用理论值冒充实测结果。

### 验证记录

- 前端全量 Vitest：81 个测试文件、526 项通过、16 项按既有设计跳过；TypeScript 检查和 Vite 生产构建通过。覆盖协议原子性、standalone 混排、工具暴露/legacy 回退、多 Skill 允许并集、联合决策互斥、重复步骤过滤、缓存失效和响应式缓存复用。
- Rust 新增并通过 `validation`、`next_stage`、Skill 工具策略和当前上下文工具可见性定向测试；`cargo fmt --check` 通过。
- Rust 整库共 91 项：87 项通过、2 项按设计忽略；仍有两个既有 Windows 环境用例失败：一个把本地 Windows 临时路径传给远端 POSIX 路径校验，另一个运行环境缺少 `bash`。本轮新增和相关定向测试全部通过，两项环境失败与模型调用和 Token 优化无关。

## 第 5 次：消除可确定协议重试并修复远端目录树工具

### 用户需求

- 继续降低重复上下文造成的 Token 消耗，不限制输入或输出 Token 数量。
- 修复 Windows 桌面端调用 `files.get_structure` 读取 Linux 远端绝对路径失败的问题。
- 保持通用编排能力、Skill 领域约束、安全门禁和最终验收质量。

### 真正修改的方案

1. `files.get_structure` 不再用宿主机 `std::path::Path::is_absolute()` 判断远端路径。根路径、排除路径、文件名提取和递归拼接统一使用远端 POSIX 语义；只在 SFTP API 调用边界临时转换为 `Path`，因此 Windows 不会再把 `/opt/app` 误判为相对路径，也不会在递归路径中混入反斜杠。
2. 前端在调用后端前执行同一套 POSIX 规范化：折叠重复 `/`，拒绝 Windows 路径、NUL、`.` 与 `..` 路径段。非法参数在本地失败，不消耗一次远端目录扫描。
3. 对完整且协议有效的 `opsark-tool` 步骤，空白 `validation` 在 Rust 模型输入边界本地规范化为字符串 `"true"`。畸形工具命令、普通 Shell 空校验和普通 Shell 的无意义 `true` 仍由原门禁拒绝；不会为修改一个确定字段重新发送系统提示、完整 Skill、工具 Schema 和任务快照。
4. 自动调整计划会与整个任务尝试历史比较。已完成命令不能重复；失败步骤只有在 `command` 或 `validation` 发生实质变化后才进入执行队列。用户明确发起的人工重试保留原能力，避免去重策略阻断有意恢复。
5. 本轮没有进一步按关键词硬裁剪 Skill 或工具。现有 `modelExposure + Skill allowedToolIds` 保守路由继续生效；更细的阶段 DAG 必须由 Skill 声明前置事实、产出事实和验收条件后才能启用，避免通过猜测当前阶段损害业务质量。

### Token 影响

- 日志中由空 `validation` 触发的联合协议回退和计划修复链将改为零次额外模型调用；按该份日志对应路径，可消除 33,273 Token 的重复消耗。
- `files.get_structure` 的宿主路径误判被根治，成功路径不再进入失败复核与相同工具重拟链；按该份日志对应路径，可避免后续 51,067 Token 的级联消耗。
- 自动模型调整即使仍返回完全相同的失败工具调用，也不会再次执行并制造下一轮模型请求。
- 上述数值是对既有日志路径的反事实估算；新版本真实收益仍以新生产日志复测为准。

### 验证记录

- Rust：远端 POSIX 路径规范化、递归拼接、排除路径安全和空工具校验本地规范化的定向测试通过。
- 前端：`fileStructure`、`taskProgression`、`agentService` 定向测试通过；全量回归发现并保留了用户明确人工重试同一命令的行为。

## 第 6 次：状态感知去重、只读批次与 Skill 渐进加载

### 用户需求

- 按优化方案提高运维 Agent 完成效率，减少重复模型调用和重复上下文。
- 不新增输入或输出 Token 上限，不牺牲审批、安全约束和最终验收；兼容自定义 Skill。

### 真正修改的方案

1. 替换第 5 次的永久命令去重策略：只比较当前目标轮次内仍有效的尝试。执行器记录目标、会话代次和凭据版本；上下文改变或实际变更发生后，允许重新观察和重试旧失败。同一上下文内已完成的变更仍受去重保护。工具参数对象按键排序后比较，键顺序变化不再绕过去重。安全门禁阻断、尚未执行的变更不使旧证据失效。
2. `files.get_structure`、`files.read_content` 和 `software.check` 声明为 `read_batch`。参数已知的纯 observe 工具步骤可以在一份计划中逐项执行，整批结束只请求一次后续计划；失败停止剩余步骤。禁止混入 Shell、变更或 standalone 工具。这是顺序批处理，不是并行远端执行，也不允许预先猜测前一步输出。
3. 新增通用 `planningContract`：全局边界、最终验收、阶段规则、工具候选集及所需成功工具证据。阶段仅控制规则加载，不作为业务完成证明；程序仍不能仅凭一次文件读取判断项目已正确部署。
4. 内置部署 Skill 先试点“项目发现 / 环境准备与部署”；源码获取 Skill 仅缩减初始准备阶段，开始执行后保守恢复完整工作流。部署阶段读取证据必须属于当前运行上下文，截断结果不触发阶段展开。领域规则由各 Skill 声明，通用编排器不硬编码 Git、Java 或 Node 关键词。
5. 增加 `context.expand` 控制工具：活动 Skill 可请求加载其完整规则和原允许工具，不能扩大原权限或取消禁止集。出现失败、用户修改 Skill 指令或没有阶段元数据时使用完整规则。展开事件不是业务成功证据，也不允许激活未选择的 Skill。
6. 去掉规划和整体复核中按固定字符截短 Skill 的行为，避免验收条款被截掉。发现续接中相同的 `output` 与 `evidence.rawOutput` 只传一份，当前步骤不再重复进入历史事实。工具已返回的正文保留供模型判断；联合快照补充当前有效工具正文，避免只剩引用和摘要而迫使模型重新读取。
7. 目录树结果向模型同时暴露 `rootPath`、`truncated`、`warnings`。沿用上一轮远端 POSIX 路径修复，完整性标记不再仅留在后端。
