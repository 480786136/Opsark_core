## 已确认问题

1. Core 对“当前/已打开 + Shell/会话”的宽泛文本匹配，把 `uptime`、`who` 等只读登录会话检查误判成修改用户已打开 Shell，导致初次规划及自动调整均被拒绝。
2. Admin 原预留算法是完整请求 UTF-8 字节数加消息余量、1,024 和最大输出 Token，并非模型输入 Token 数。该用户任务前可用 99,899，五次成功调用实际消耗 46,747，剩余 53,152，预留为 0；首个失败请求却要求预留 93,074，随后约 77,000。
3. 最后十次请求均在上游派发前收到 `402 INSUFFICIENT_CREDITS`，没有扣费或占用余额。Core 把错误概括成“后续方案暂未就绪，可稍后重试”，且未针对额度条件未变化抑制重复规划。
4. 十次请求是独立调用，不是单次 HTTP 自动重试。日志不能证明全部由自动循环触发，不能据此声称存在十轮自动自旋。

## 本轮修复方案

### Shell 执行范围

- 区分只读查看会话与明确操作用户已打开 Shell/PTY，不用部署软件名称等专用业务白名单。
- 保留用户 PTY 不能由 Agent 注入的安全边界，不能仅凭 `kind=observe` 放行危险操作。
- 回归覆盖真实中英文只读描述、危险注入误标只读、合法 `user_action` 与其他执行范围校验。

### Admin 额度预留

- 改为明确标识精确程度、包含安全余量的输入 Token 计数/估算策略，避免将整个 JSON 字节数当作 Token。
- 保留原子预留、实际 usage 结算和超出预留时的待核对保护；不按余额强行截低预留、不透支、不篡改上游 usage。
- 不足错误携带可用额度、所需预留额度及估算说明，支持 Core 展示和判断是否值得重试。
- 回归覆盖正余额拒绝、成功结算、拒绝不派发/不扣费及并发安全。

### Core 模型错误与恢复

- Rust 到前端保留结构化 HTTP 状态、错误码、可重试标记与额度明细，不仅传字符串堆栈。
- 额度不足提示真实原因；在额度/模型等有效条件未变化时阻断重复规划，同时保留可恢复路径与已有执行证据。
- 同时验证 discovery 续接和托管调整路径，不能只修手动按钮。

## 实施结果

### 1. Shell 规则

`src/features/agent/executionScope.ts` 改为关联用户现有 Shell 目标与肯定操作意图，区分观察句式、状态名词、否定说明和 Agent 自有上下文。增加直接终端注入形式的独立检查，并遮蔽引号中的普通数据，避免打印或搜索 `tmux send-keys`、`TIOCSTI` 文本被误判。

这是通用执行范围修复，不使用 Kubernetes、软件名称或特定任务 ID 白名单。静态规则不能识别任意脚本的全部行为，执行器隔离与 `user_action` 不自动执行仍是安全边界。

### 2. Admin 预留与结算

- 新增 `Opsark_admin/app/token_estimation.py`，按真实输入内容及结构估算，不重复计算 HTTP JSON 转义。普通拉丁字母、数字、常用汉字分类估算；长不透明串和罕见 Unicode 采用更保守回退，再加 30% 余量、消息开销及 1,024 固定缓冲；输出上限全额预留。
- `estimator` 明确标识启发式版本，`exact=false`。本轮没有引入或下载供应商 tokenizer；这不是精确 Token 计数，也不是所有输入的严格上界，不能用它替代实际计费。
- 保留 256 KiB 请求大小限制、原子预留和按上游真实 usage 结算。若 usage 缺失、非法或超过预留，保持待核对，并阻止该用户继续累积新的官方调用；不影响其他用户。
- 预留准入与待核对转换使用同一账户行锁；管理员核对真实超额时，在余额足够前提下原子追加差额并结算，失败则维持原预留/账本，重复核对不重复扣费。
- `INSUFFICIENT_CREDITS` 返回可用/已预留/所需预留/估算输入/输出上限等结构化明细与 `retryable=false`。新增 `CREDITS_RECONCILIATION_REQUIRED` 区分待核对阻断。
- 被拒调用在扣费事务回滚后独立记录元数据，方便 Admin 列表解释拒绝原因，不保存请求正文、不创建预留、不产生 Token 扣费。历史被拒请求不会自动补写。

### 3. Core 错误与恢复

- `src-tauri/src/model.rs` 与 `lib.rs` 保留 `modelError` 结构，避免叠加工作流 trace 时丢失状态码和额度明细；终止型 HTTP 错误不因非 JSON 响应再次重试。
- `src/services/backend.ts` 解析错误类型，说明“本次预留不足”和“估算并非实际扣费”，不把余额大于零等同于余额耗尽。
- `OpsTask.modelPlanningBlocker` 持久化阻断信息，初始计划、发现阶段续接、手动调整及托管队列使用统一门禁。已有目标、Skill、已完成步骤和执行证据继续保留。
- 未改变有效条件时，重复点击只进行本地检查，不调用模型；模型、预算、目标/证据等实际条件变化，或刷新后额度确有改善，可以恢复。展示文案、失败计数、余额 revision 单独变化、旧缓存刷新到拒绝时余额不算恢复证据。
- 错误审计同时保留 message 与 stack，避免 WebKit 的 stack 只有调用位置、看不到真实拒绝原因。
- 阶段联合决策遇额度错误不再降级发起第二次付费目标复核；目标复核自身也保留该错误交由任务门禁处理。普通网络错误的既有降级逻辑保留。
- 普通调整请求补充 `triggerSource/automatic` 审计，便于后续区分自动队列与用户点击。

## 上线与局限

- 需要重新加载/启动 Admin，并重新编译启动 Core（含 Rust），已安装旧客户端不会仅因源码修改自动更新。
- 本轮没有新增数据库迁移或依赖；不替代工作区其他既有用户体系改动所要求的迁移步骤。
- 估算下降不意味着任意大上下文都能被现有余额覆盖；余额仍不足时应显示所需额度并停止重复请求，而不是为了放行把预留截到余额。
- 本轮没有重放该任务的服务器命令，也不把单元测试或离线重算描述成线上业务已经完成。
