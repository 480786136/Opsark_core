## 基线与问题结论

用户提供的 32 次 Admin 调用合计输入 391,402 Token、输出 25,914 Token，其中计划生成输入约占 78.7%。高消耗并非单纯由模型回答过长造成，主要来自计划/复核阶段重复携带历史快照、工具 Schema 和相同执行输出，以及无进展长任务的周期性重复复核。

目标日志暴露出三个业务正确性问题：

1. 用户已经确认 `image_registry=registry.aliyuncs.com/google_containers` 和 `cni_manifest_source=mirror_url`，但执行失败复核未携带该决定，模型错误判断为“用户尚未回答”。
2. `kubeadm config images pull` 已失败，后续普通 `kubeadm init`、Flannel 部署却被宽泛的“配置/部署/安装”关键词误判为恢复路径，存在带故障继续执行的风险。
3. `completed + executionStatus=success + observationStatus=unknown` 的正常步骤被写入 `unresolvedIssues`，旧问题不断进入后续上下文并放大 Token。

此外，Core 开发者日志原先没有保存 Admin 返回的请求 ID，难以把 Admin 的 Token 记录直接关联到 task/round/phase/step。

### 5. 长任务与自动循环减少无效模型调用

## Token 与上下文管理策略

当前上下文分为三层：

1. 长期小事实：整体目标、授权边界、已确认非敏感输入、凭据引用、Skill。

## 第二轮复查与优化（文档先行）

### 复查结论

第一轮修复方向正确，但“严格恢复、必要约束完整保留、长期任务不误中断”的验收结论过满。本次已获用户授权继续修正，以下内容先于第二轮代码修改记录。

- 恢复关系依赖关键词、命令动作或路径交集：两个命令都包含 `/dev/null` 即可能误判；后面的恢复步骤也可能放行前面的普通变更。
- 长任务前三次采样均有 CPU/I/O 进展，第四次一次采样失败即可误中断。
- 局部修复只复制顶层字段，遗漏 `baseSnapshot.executionConstraints` 与 `baseSnapshot.task.permission`。
- 未解决问题直接截到最近 16 条，丢失模型可见的早期阻断；旧检查点未迁移，已有伪故障继续污染上下文。
- 用户决定缺少目标/服务器适用范围，需要避免目标变化后复用过期输入。

### 第二轮实施方案

1. 恢复流程改用结构化关联与顺序门禁：明确失败步骤、目标、恢复或复验目的；保留真实失败，只有关联验收证据能解除阻断。旧计划缺少信息时进入调整。命令风险识别继续用于副作用防护，领域关键词不作为恢复放行依据。
2. 建立必要约束投影：从原始或嵌套上下文统一保留目标、权限、执行边界、已确认决定；局部修复压缩历史正文但不能丢失约束。
3. 分离文本进展、运行态进展和采样失败：退避减少模型调用，采样暂不可用不能证明业务无进展；采用明确的运行期限管理终止。
4. 检查点升级迁移：依据可用执行记录重建旧检查点；完整保留未解决问题索引，按预算展开正文并显式标记遗漏。
5. 用户决定绑定目标和服务器，过期决定退出有效投影；有效决定的索引和内容预算分开管理。
6. 补充上述反例回归，执行类型检查、构建与相关测试；实际 Token 节省以新运行时请求计量，不把字符数或减少复核次数当作完整线上计费结果。

### 第二轮实现说明

1. **通用恢复契约**：新增可选 `PlanStep.recovery`，由 `failedStepId / targetContext / purpose` 表达诊断、修复、复验关系，前后端协议和规划上下文一起支持。不能因为后面的步骤可能恢复，就越过前面不相关的业务步骤。自动推进和直接执行入口均复核权限与恢复关系；`best_effort` 检查全部阻断，不能掩盖较早硬失败。修复命令返回成功不等于事故解除，必须重新执行既有验收契约并取得真实成功证据；原失败记录保持 `failed`。成功观察到阻断的步骤仍保持执行成功事实，不混同于命令失败。复验保留原 expected/作用域，并拒绝常见空验收、失败吞码和矛盾证据。
2. **上下文必要约束**：调整、下一阶段和复核显式保留整体目标、权限与执行约束。Rust 单步骤修复支持从旧 `baseSnapshot.task.permission`、`baseSnapshot.executionConstraints` 回取必要约束，优先使用当前顶层权威值，不复制历史正文。

4. **输入去重与预算**：完整非敏感决定索引与最多 16 项、约 6,000 字符的展开正文分开管理，优先展开当前计划引用的旧决定。历史表单原文、旧 `result.facts/evidence.facts` 不再从 `previousExecution`、发现上下文、已知事实和复核入口绕过范围过滤。初始需求入口同一轮输出不再同时进入 `previousExecution` 和 `knownExecutionFacts`，后者使用引用。原始审计台账不改写。

6. **运行监控**：文本沉默、实际 CPU/I/O 进展、采样失败分别计量；采样失败不能推导为业务失败。progressive 的 120 秒改为复核退避起点，最高 600 秒；可信调用者可传入启动时冻结的 `executionDeadlineAt`。常驻服务单独处理，仍需真实退出/独立验收。当前没有为 progressive 新增默认硬超时，既有 bounded 90 秒规则保留。

### 通用性与兼容边界

- 恢复放行不再依赖 Kubernetes、包管理器、操作名称或共享路径关键词；这些是业务流级修复，不是部署某种软件的脚本。
- **结构化关联不等于修复语义的证明**：程序能核验失败 ID、服务器/轮次、执行顺序和原始验收结果；不能仅凭模型填写 `purpose=repair` 就证明任意 Shell 命令确实修复原资源。恢复提案仍受权限、只读边界及原有风险审批控制；资源级自动修复白名单/工具契约尚未全面建立。不得把本轮描述成“所有错误恢复命令都可被语义识别”。
- 现存命令副作用识别和长任务 workload 兼容识别仍含软件规则，用于风险防护/旧计划默认分类，不作为“恢复成功”的证据。
- `best_effort` 不等于把失败改成成功；显式用户约束下可评估仅观察到的前置风险，但实际执行/验收失败不能由模型口头抹去。
- 未恢复的风险允许尝试后，任务可能仍处于待验收状态；本轮未建立独立的“用户接受残余风险即带风险成功”状态。若需要改变原验收条件，应明确更新目标/授权，而不是让模型自行取消阻断。
- `PlanStep.recovery` 是可选协议扩展，旧任务缺字段不会被猜测为恢复步骤；前端与 Rust 后端应一起构建更新，不能混用不支持该字段的旧后端。
- 输入和问题的完整索引会随数量增长；当前预算限制的是正文，不声称整个请求拥有固定 Token 上限。过期/旧范围输入保留在本地，不作为当前授权。
- 旧检查点已截掉的问题，如果原始台账也已缺失，无法凭空恢复。迁移会暴露覆盖缺口，而不是宣称历史完全修复。
- 本轮没有执行线上任务、调用付费模型 API 或操作 Kubernetes/SSH 服务器；实际 Token 节省仍需更新后的 Core 请求与 Admin 计量对照。
- 验证过程中误生成的 275 个临时 JavaScript/构建索引产物已移至 `/tmp/opsark-generated-js-9vSvvz`，可恢复；不进入交付代码，原 TypeScript/Vue 源码未删除。

- Rust→前端→协议修复→日志全链路保留错误对象；不再用“第 N 个计划步骤”等中文文本正则决定修复字段。
- 给模型的反馈说明违反的具体规则、允许修改的字段及禁止改变的业务含义；命中片段按需要截取并脱敏，不为定位错误复制整个任务历史。
- 主要模块：`src-tauri/src/lib.rs`、`backend.ts`、`planNormalizer.ts`、`recoveryContract.ts`、`types.ts` 和对应日志类型。
- 验收：现场命令明确显示“diagnose 命令含副作用”，并定位 command；不得继续显示为缺少已有的 recovery 三字段。

#### P0-3：诊断命令满足真实只读要求

- 统一规划提示与校验规则：只读诊断不能创建临时目录/文件、写入或删除目标文件，也不能用 `kind=observe` 掩盖实际变更。
- 为保留退出码而调整管道时，优先采用不落盘的采集方式，分别保存真实退出码和输出；不能通过 `|| true` 或后续打印覆盖关键命令失败。
- 对此次 `mktemp → 输出重定向 → rm` 链整体修复；只删 `rm` 会残留临时目录，不能作为通过方案。
- 副作用识别检查实际命令结构，区分执行动作、引用文本、注释及允许的重定向；例如写 `/dev/null` 与创建目标文件不能简单等同。包查询命令也需核对是否刷新缓存等实际行为。
- 不把 `purpose` 改成 repair 或放宽授权来让原诊断通过；确实需要变更时转入正常业务调整，并提供独立验收。
- 主要模块：共享副作用规则、`validation.ts`、`src-tauri/src/command_guard.rs`、`src-tauri/src/lib.rs` 的规划/修复提示。
- 验收：诊断修复后无临时资源遗留，失败退出码仍可追踪；真实副作用被拒绝，单纯引用命令名称不会被误判成执行该动作。

#### P0-4：语义指纹与无变化修复终止

- 对计划行为字段计算稳定指纹：kind、命令、验收、expected、风险、执行作用域、恢复关系、运行与会话设置、工具及参数等；保留步骤顺序，排除新生成的步骤 ID、时间戳和不影响执行的文案变化。
- 这里的“语义指纹”用于识别相同执行内容，不声称能证明任意两段 Shell 语义等价。对象键顺序稳定化，本计划内部生成的 ID 引用按稳定步骤位置映射；命令字符串不做可能改变引号、换行或参数含义的粗暴空白压缩，历史失败 ID 与目标引用仍参与比较。
