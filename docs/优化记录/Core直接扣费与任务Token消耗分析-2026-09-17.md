# Core 直接扣费与任务 Token 消耗分析

## 本轮要求与实施前方案

- 按用户要求，官方模型新请求不再预留额度；模型结束后按实际输入加输出 Token 直接扣可用余额。
- 取消按请求估算量拒绝正余额调用，不影响请求大小、输出上限及鉴权限制。
- 保留幂等调用记录与原子结算；无法获得用量或余额不足结算时记待核对/待扣，不伪造零消费、不扣负余额。无预留不能保证所有已发出的并发请求都能结算，这是本轮主动接受的策略取舍。
- 历史预留记录仍可按原规则结算，不自动改写旧账本，不退还已经实际消耗的 Token。新请求复用原调用账务表但预留金额为零，仅记录调用身份和结算状态。
- 更新 Core/Admin 的额度文案，并使历史预留不足造成的任务阻断在新直接扣费策略下可以恢复。
- 对 `task-1789637806744-z8gdp0` 做只读日志分析；本轮不自动重放该任务或扩大修改规划策略。

## 直接扣费实施结果

- Admin 的网关已从 `reserve` 改为 `begin_direct_call`，不再调用估算器决定是否派发。新调用只记录 `amount=0 / pending_usage` 的幂等账务记录，不修改可用或预留余额，不新增 reserve 流水。
- 已知真实用量按输入加输出原子扣账，流水类型 `usage_debit`，同一调用的并发/重复结算只扣一次；未派发不扣费。历史金额大于零的预留仍走旧结算逻辑。
- 未知用量或实际用量大于余额时进入待核对；后者保存完整真实待扣数，不截断、不制造负余额。管理员补足余额后可按原核对接口完成直接扣账，不会先补预留。已记录的真实待扣数不能被改成零来绕过结算。
- 超过 20 分钟仍没有完成状态的直接调用也阻止继续累积未知用量，需要核对；正常并发请求允许进入，不通过隐含冻结实现“假取消预留”。
- `/me` 的 `billing_mode=direct` 经 Rust 投影为 `billingMode`。Core 的任务阻断指纹包含计费模式，因此刷新账号确认服务已经切换后，旧的预留不足阻断可以解除，不要求再充值；新的零余额/待核对错误仍保留明确提示及防重试保护。
- Core/Admin 额度展示已区分直接扣费、待核对用量和历史预留。无新增依赖和数据库迁移；保留旧估算器与旧预留处理仅用于历史兼容/测试，新网关不使用它们预留额度。

## Token 高消耗的原因及证据

### 1. 补读阶段结束后再次完整规划

第一次阶段联合决策生成 2 个 `evidence.read` 和 4 个后续 Shell 检查。只读批次拆分后执行了补读前缀，又发起一次完整续规划，输入 16,512；第二次联合决策同样生成补读及后续检查，补读后续规划输入达到 24,312。

代码路径为 `backend.ts` 的阶段前缀拆分，以及 `agentContext.ts` 的 `buildContinuationContext` / `agentService.ts` 的发现阶段续规划。拆分是协议要求，不能简单取消安全边界；但后续已有计划没有作为可复用草案接续，形成“决策生成后续步骤 → 补读 → 再生成后续步骤”的重复规划开销。新证据可能确实要求调整，不能把全部续规划用量断言为浪费。

### 2. 历史证据反复进入较大的上下文

以下是对应 JSON 字段的 UTF-8 字节数，不是精确 Token 分摊：

- 首次规划的动态消息约 3,164 字节；最后一次联合决策动态消息约 67,398 字节。
- 第一次联合决策 `baseSnapshot` 约 24,426 字节，最后一次达到 63,321。
- 最后一次快照由 `recentPhases` 约 23,189、`currentPlan` 约 19,918、`historyCheckpoint` 约 16,199 字节等组成。
- 两次补读后的完整续规划中，`knownExecutionFacts` 从 20,700 增至 43,458 字节，后一次的 `completedSteps` 占 42,532；同时还携带约 8,642 字节的 `completedDiscovery`。
- 普通规划固定系统消息约 15,455 字节，工具目录消息约 12,975 字节，其中工具 Schema 约 12,895；多次调用重复携带。

因此并非单一“历史消息越来越多”，而是固定协议/工具目录加当前计划、近期阶段、检查点及补读输出的多个投影累积。现有去重和单段截断并不等于全请求有统一预算。

### 3. 安全修复与修复越界再次消耗模型调用

- 第一处局部修复针对 `EMPTY_SUCCESS_FALLBACK`，消耗 4,398 Token。
- 充值后的完整调整方案消耗 22,456 Token；第 6 步触发 `PIPELINE_STATUS_LOST`，局部修复又消耗 4,604。
- 该修复引入 `yum -C check-update > /tmp/yum_checkupdate.out`，只读步骤却写临时文件，触发 `OBSERVE_COMMAND_MUTATION`；再次修复消耗 4,627，但返回修改超出了许可字段范围，最终计划没有执行。
- 随后用户发起新的业务重规划，再消耗 22,366 Token。

这里部分调用用于正确的安全保护，不应为了省 Token 放行吞退出码或写文件的只读命令。应改善初次命令生成与局部补丁协议，减少生成不合规方案再修复的概率。本次不是此前的 Shell 会话描述误判。

### 4. 观察与交付没有充分收敛

日志中多轮重复检查内存、失败服务、容器组件及磁盘。第二次成功联合决策明确承认已有 19 条结构化证据，但仍以“优化建议尚未形成”和证据冲突为由继续检查。

补查并非全部没有依据：原始 `iostat/mpstat/top` 与 `uptime/ps` 输出确实存在 CPU/负载口径冲突，不能直接认定为模型胡编或解析列错误；本轮没有连接服务器验证冲突来源。问题在于流程没有充分区分“证据采集是否足够交付”与“最终建议是否已经写出”，容易在交付尚未发生时继续扩大检查，而不是输出已确认结论、风险分级和明确的不确定项。

## 后续优化建议（本轮仅分析，未修改这些规划策略）

1. **先修交付收敛**：对“检查并给建议”区分必查项、阻塞证据和可选深挖；核心证据齐备后生成带不确定项的建议，不能仅因还没写建议就再次安排检查。
2. **接续已有草案**：阶段拆分时保留后续步骤草案及依赖，补读后只复核受新证据影响的步骤；不重复发送一次完整规划请求。
3. **统一上下文预算**：建立任务事实表与 evidenceId 索引，近期阶段/检查点不反复展开相同事实；按当前决策缺口取原文，保留已读范围，避免同一端口/日志证据跨阶段重复补读。
4. **局部修复更小、更严格**：只传受影响字段和相关规则；针对 exit 状态、管道、只读输出规范优先使用已验证模板或确定性转换。修复越界不转成多轮大上下文循环。
5. **分阶段裁剪工具目录并增加软预算提醒**：只带本阶段可用工具 Schema；累计已用 Token、修复次数和无新增事实轮数，在继续深挖前展示成本提醒。软预算不是恢复本轮已取消的额度预留。

取消预留只解决“有余额却因估算门槛提前拒绝”，不会自动降低上述 152,617 的真实用量，更不会返还已经消耗的 Token。
