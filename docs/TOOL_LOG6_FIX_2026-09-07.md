# 开发者日志记录 6：工具故障修复与关联问题

分析文件：`docs/开发者日志记录6.json`。文件实际为时间线文本和多段 JSON，不能按一个 JSON 对象解析。主要任务 `task-1788695974630-6j43s7`，目标“检查当前mysql有哪些库”，最后状态为等待输入。

## 根因与修复

1. **凭据表单契约不明确，触发反复模型调用。** 818、2336、2979、3621 行的 combinedFallback 均为 credential username 被生成成 text，但执行器要求 password。已有工具说明仅强调“敏感值”，未明确用户名也走保密存储。本轮在模型命令解析入口将显式 credential.role=username 且 type=text 的字段局部提升为 password，再运行完整契约校验；不猜测角色、不改变目标、用途、必填要求或凭据配对。规范化后的命令写回计划，因此审批和执行使用相同参数。未声明凭据的敏感 text 字段仍拒绝。
2. **格式修复重写了计划内容。** 792、804、1603 行拒绝 description/kind 改写。安全约束保留；修复指令明确逐字保留不可变字段，仅修改错误参数。本地类型规范化消除了本次日志最常见的重试起点，并未放宽模型改写权限。
3. **工具元数据混进步骤协议。** 1617 行模型把 planMode 写到 steps 中，触发 unknown field。阶段规划提示现明确 planMode/completionMode/executionMode 只属于工具目录，不能作为步骤字段。严格反序列化仍保留；这是生成提示改进，不保证所有模型不再产生额外字段。
4. **最终表单的目标与交互不正确。** 777 行 credential.target 使用 mysql_target，占位目标可能污染凭据复用；同时 no_instance 与必填主机、用户名、密码并存，无法自然表达“无目标”。数据库 Skill v2 改为目标未知先澄清、目标确定后收集一个完整凭据组，禁止虚构目标和互相冲突的必填表单。工具 schema 描述同步明确配对、保密类型与已知目标要求。这部分是规划约束，并未新增通用的条件表单引擎或真实目标证明器。

## 其它问题

- **Java 查询存在假阳性。** 4452 行附近的旧任务摘要承认三条记录全是检查自身的 bash/sh 进程，但 4478 行之后的程序证据仍是 processFound=true、processCount=3。已修复进程观察适配器：识别本次检查命令或 Opsark 执行包装器的 Shell 输出时，标记 unknown / processEvidenceAmbiguous，不再生成“发现目标进程”的肯定事实。正常 Java 进程和真正空结果保留原处理；该检查不承诺识别任意重写或混淆后的自匹配。
- **负面证据被过度泛化。** 未找到客户端、常见 socket、目录、进程，不等价于未安装任何实例；容器、自定义路径和端口可能未覆盖。Skill 现在要求保留范围与未知项，合并独立探测，在无法定位后及时澄清，不无依据穷举远程实例。
- **使用 echo 代替提问。** 818 行之前的阶段只输出“请提供参数”，但没有进入输入工具。Skill 明确提问必须使用 user.request_input，Shell 输出不算已向用户收集信息。
- **过宽的配置/环境采集。** 3585 行计划读取完整配置和 DATABASE_URL 类环境变量，可能包含凭据；已有脱敏不应成为无界采集的理由。Skill 改为有依据的路径与必要非敏感字段，禁止完整历史、环境和连接串采集。
- **新旧任务上下文仍混用。** 4370 行后的 MySQL 需求处理上下文仍带旧 Java taskId、目标和执行详情；这与“先分类并规划、后创建新任务”的现有流程一致。会话展示与任务证据隔离还需要在初始规划入口彻底分开，本轮未进行该架构迁移。
- **Token 成本主要来自额外往返和重复上下文。** 此文本包含 5 次 combinedFallback：4 次用户名类型错误、1 次 planMode 协议错误；同一错误在上下文摘要中还会重复出现，不能将全文字符串次数当调用次数。文件未提供完整供应商 usage，无法计算实际 Token 或费用降幅。
